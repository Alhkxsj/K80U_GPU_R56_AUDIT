# 06 — ABI 三元组兼容矩阵

> **本文件回答任务书的最终问题**：是否存在 `R56p0 Kbase + 原厂 CSF 固件 + 原厂用户态 DDK` 的可行组合？
>
> **答案**：**不存在**。理由是**源码判据 + 实测读数**：r56p0 只接受 header `0.4`，用 `!=` 严格校验且无 fallback；r49p1 只接受 `0.3`；而原厂固件的实际 header 值**已实测为 `0.3`**（`6e 3a f1 c3 03 00 00 00`，[D·A]，`02` §3.0.5）。
>
> **但**存在一个更乐观的替代：`R56p0 Kbase + R56p0 固件 + 原厂用户态`（组合 C）在**契约层是兼容候选**。
>
> 证据等级：**[D·A]** 厂商分区静态实测 · **[D·B]** 第三方内核运行时 · **[D·C]** 厂商模块 · **[E1]** 源码/二进制直接证据 · **[E2]** 交叉推导 · **[E3]** 惯例推断 · **[U]** UNKNOWN
>
> **⚠️ 更正记录（五项，按轮次）**：
> 1. 组合 B 的否决理由从"实测 0.3≠0.4"改为"**源码判据 + E2 推理**"（`02` §3.0）——第二轮，因当时无字节；
> 2. "gralloc/mapper/HWC 免疫"**撤回**（`05` §3.2）；
> 3. "Vulkan 无法判定存在性"**改为"已确认存在"**（`04` §1）；
> 4. **组合 A 的"在用"须限定环境**：设备运行的是厂商 GPU 模块 + **第三方 GKI 内核**（KernelSU 补丁），不是原厂 boot。因此"A 可用"只被证明"在第三方内核上可用"（`08` §2、§7）。
> 5. **第三轮（2026-11-15 23:20）**：组合 B 的否决理由**回到"实测"**，且这次有字节支撑——原厂固件 header 实测 `0.3`；同时 DDK 实测 `r49p1-03bet0`，与 kbase 同串。**组合 B 的证据等级从 [E1]+[E2] 升为 [E1]+[D·A]。**
> 6. **第五轮（2026-11-16 收尾核验）**：①§2.3.3 原判"padding 不构成门槛"**撤回**——实为 48 个钩子中 15 个强制校验（原统计只看了前 20 个定义），R-C2 由"tiler 失效"上调为"GPU 不可用"；②新增 §2.3.2 的 R-C3 机制说明（props 两阶段协商）。组合级结论**一条未变**。详见 [`09_stage4_closure.md`](09_stage4_closure.md)。

## 0. 关键判据回顾（四行决定一切）

## 1. 四组合总表

| 组合 | Kbase | 固件 | 用户态 | 判定 | 主因 |
| :---: | --- | --- | --- | :---: | --- |
| **A** | r49p1 | 原厂（**实测 0.3**） | 原厂（**实测 r49p1 → 1.30**） | ✅ **在用**（厂商模块 + **第三方 GKI 内核**） | 三者同代，自洽；kbase 串 `r49p1-03bet0 (UK 1.30)` **[D·C]**、DDK 串 `r49p1-03bet0` **[D·A]**、固件 0.3 **[D·A]** |
| **B** | R56p0 | 原厂（**实测 0.3**） | 原厂 | ❌ **不可用（实测否决）** | r56p0 只认 `0.4`，原厂实测 `0.3` → `-EINVAL` **[E1]+[D·A]** |
| **C** | R56p0 | **R56p0 0.4** | 原厂 | ⚠️ **契约层兼容候选** | UAPI 全兼容；用户态需**整套**保留（含 `libged`/`libgpud`）**[E1]+[D]** |
| **D** | R56p0 | R56p0 0.4 | R56p0 1.39 | ⚠️ **理论自洽，需平台层适配** | TASK 03 的 45 处结构体 + 89 处符号 |

> **组合 A 的证据等级本轮升级，但升级有边界**：它不再只是"源码自洽"，而是"**设备正在这样运行**"。这是全表唯一有 [D] 背书的组合。
>
> **边界**：观测环境是**厂商 GPU 模块 + 第三方 GKI 内核**（KernelSU 补丁，`6.6.143`，源码提交 `f9aa2fec`），**不是原厂 boot**。所以 A 的 [D] 只能读作"厂商模块在重编 GKI 内核上可用"，不能读作"原厂环境验证通过"。
>
> **2026-11-16 两度补正**：原文写"前者恰好证明 GKI KMI 未被破坏"；随后一度改为"该内核绕过了 `same_magic()` 校验"。**后一说法已撤回**：`CONFIG_MODVERSIONS` 下 `same_magic()` 只比较第一个空格之后的 flags 段，两侧逐字符相同，**装载合法、无需补丁**（`08` §3.7.4、`09` §2）。现行读法：装载成功**可以**作为"被 import 符号 CRC 一致"的证据，前提是该内核的 `check_version()` 未被 `allow_version_mismatch=true` 构建打开过（U4-25b）；它仍**不能**证明"A 在原厂环境可用"。

### 2.3 组合 C — 换内核 + 固件，保留原厂用户态（⚠️ 候选）

这是**最值得关注**的组合，因为它对应"最小替换范围"。

| 维度 | 结论 | 等级 |
| --- | --- | --- |
| **初始化兼容性** | **通过**：`handshake` 取 `min(39, claim)`，因 claim ≤ 30 故内核以 ≤1.30 语义服务 | **[E1]** |
| **UK ABI** | 有效版本恒 ≤ 1.30。能力表中 1.31/1.32/1.35 的新能力**全部不生效**，旧行为被完整保留 | **[E1]** |
| **CSF 协议** | 固件 0.4 与内核 r56p0 自洽（官方配套）。**但用户态 ≤1.30 对固件行为的期望**属 **[U]** | [E1]/[U] |
| **GPU 属性查询** | 83 ID 值不变，新增 86/87/88 追加；两阶段 size 协商不越界 | **[E1]** |

| **GLES 初始化** | 契约层通过；实现层需**整套**保留 `libGLES_mali.so` + `libged` + `libgpud` + 4 个 gralloc 私有库 | [E1]/**[D]** |
| **Vulkan 初始化** | **不是独立问题**：薄壳 NEEDED `libGLES_mali.so`，与 GLES 同生共死 | **[D]** |

#### 2.3.1 为什么说"契约层兼容"是有分量的结论

不是"看起来差不多"，而是六条独立证据：

| # | 证据 | 强度 |
| ---: | --- | --- |
| 1 | 28 个共有 ioctl 的 `_IOW/_IOWR` 三元组**逐字相同**（编号空间未重排） | 强 |
| 2 | 30 个共有结构体**仅 1 个字段改名**（`mem_sync.handle`→`gpu_va`，布局不变） | 强 |
| 3 | CSF 专有 13 个结构体（`cs_queue_register/bind/kick` 等主干）**字段零差异** | 强 |
| 4 | 内存标志位 CSF 视图 **24/24 一致**，bit20/27 两版都标注"JM 专用" | 强 |
| 5 | `gpu_props` **83 个属性 ID 值全部不变**，新增 3 个 ID=86/87/88 **严格追加** | 强 |
| 6 | 能力表**显式为 1.30 保留旧语义**（含 `CSG_CS_USER_PAGE_ALLOCATION` 1.35 门槛，1.30 下走旧路径） | **最强** |

第 6 条是关键：它证明 r56p0 不是"碰巧兼容"，而是**主动设计了兼容窗口**。

#### 2.3.2 组合 C 的真实风险面（不是"能不能启动"，而是"跑起来对不对"）

| 风险 | 描述 | 等级 | 若发生的影响 |
| --- | --- | --- | --- |
| R-C1 | DDK 调用被删的 5 个 ioctl（GWT×3 / HWCNT_SET / DISJOINT_QUERY） | [U] U4-14 | 性能计数功能失效；渲染不受影响 |
| R-C2 | DDK 未清零 padding，`MEM_JIT_INIT` / **`CS_QUEUE_REGISTER` / `CS_QUEUE_GROUP_CREATE*`** 返回 `-EINVAL` | [U] U4-04c | ~~tiler heap 不可用 → 渲染可能失败~~ → **2026-11-16 上调：CS 队列注册失败 → GPU 完全不可用**；**同日后二次修正（D-027）：后果不变，但可能性下调为「中」**——结构体布局已证无实质差异，R56 对旧版本逐字段迁移（`09` §11.1） |
| R-C3 | DDK 严格校验 props 字节数（多 32 字节报错） | [U] U4-15 | GPU 属性查询失败 → 初始化中止 |
| R-C4 | DDK 依赖 `HWCNT` 通知做 DVFS 联动 | [U] U4-16 | 频率策略退化 → 性能下降 |
| R-C5 | 固件 0.4 的默认配置（progress timer 等）与 1.30 DDK 的假设不符 | [U] | 调度行为差异 → 性能/稳定性 |

> **R-C2 是唯一可能「致命」的**（后果层面）。其余都是「功能/性能降级」。
>
> **但它的「可能性」已被 D-027 下调**：R49 与 R56 的 51 个共同结构体实质差异 0，且 R56 为旧版本保留了逐字段迁移路径。剩余风险只来自「R49 DDK 是否遵守自身 UAPI 的 `must be zero` 契约」，而该契约在 R49 头文件中是明文。

#### 2.3.3 两个曾被误判的风险

| 曾担心的风险 | 实测结论 |
| --- | --- |
| padding 校验构成新门槛 | ~~**排除**。`check_padding_*` 绝大多数 `return 0`；`MEM_SYNC` 由 Arm **主动替用户态清零**~~ → **2026-11-16 更正并撤回**：48 个钩子里 **15 个强制校验**（原统计只看前 20 个定义），含 `CS_QUEUE_REGISTER` / `CS_QUEUE_GROUP_CREATE*` / `CS_QUEUE_GROUP_TERMINATE` / `CS_TILER_HEAP_INIT`。**门槛真实存在**，见 `03` §9、`09` §5 |
| props 字节数严格校验（R-C3） | **机制已确认**：`kbase_api_get_gpuprops` 先 `size==0` 返回所需长度，仅当 `size < prop_buffer_size` 才 `-EINVAL`。故只有 DDK **写死 568** 才会失败；若它做了一次 size=0 探测则不受影响。DDK 是否探测 = [U]（`09` §5.4） |

## 3. 最小替换范围（核心回答）

### 3.1 结论

> **最小替换范围 = Kbase + CSF 固件（两件套）**。
>
> 用户态 DDK **在契约层可以保留**——这修正了此前"用户态也必须同步替换"的假设。

### 3.2 与 TASK 03 结论的关系

| 阶段 | 结论 | 本阶段的影响 |
| --- | --- | --- |
| TASK 03 | 保留 10 / 适配 2 / 重写 0（针对**平台层**） | 不变 |
| TASK 03-REA | 45 处结构体 + 89 处符号，P3 难度高于预估 | 不变 |
| **TASK 04（本文）** | **用户态可保留**（契约层） | **缩小**了替换范围 |

### 3.3 完整替换清单

| 组件 | 组合 C 是否需要换 | 依据 |
| --- | :---: | --- |
| `mali_kbase_mt6991_r49.ko` | **必须换** | 换版主体 |
| `mali_csffw.bin` | **必须换** | r56p0 只接受 0.4（源码判据）**[E1]**；原厂实测 0.3 **[D·A]** |

## 4. 为什么"组合 C 不可直接宣布可行"

任务书要求："如果证据不足，必须标记 UNKNOWN，不允许给出肯定结论。"

组合 C 的证据缺口：

| 缺口 | 性质 | 为什么关键 |
| --- | --- | --- |
| 原厂 `libGLES_mali.so` 的实际行为 | **行为证据**（非契约） | 契约兼容 ≠ 实现遵守契约 |
| 固件 0.4 的运行时 GLB 版本 | 固件实体 | 决定 §5 门槛是否真被满足 |
| 1.30 用户态对 0.4 固件行为的期望 | 交叉语义 | 这是唯一"两版都没覆盖"的空白 |

**特别强调第三项**：这是组合 C 的**结构性盲区**。

```
用户态 1.30  ──(UAPI 兼容)──▶  内核 r56p0  ──(同代配套)──▶  固件 0.4
     │                                                          │
     └──────────── 期望的 GPU 行为（未知） ◀────────────────────┘
```

内核在中间做了"语义翻译"，但**固件的实际调度行为**（progress timer 默认值、idle 检测阈值、CSG 抢占策略）由固件自身决定，用户态无法直接约束。若 0.4 改变了这些默认值，1.30 DDK 的性能调优假设可能失效——**表现为性能异常而非功能故障**。

## 5. 决策建议

## 6. 最终回答

### 6.1 任务书六问

| # | 问题 | 答案 | 等级 |
| ---: | --- | --- | --- |
| 1 | 原厂 `libGLES_mali.so` 能否与 R56p0 Kbase 配合？ | **契约层可以**（28/28 ioctl、30/30 结构体、83/83 属性 ID、能力表保留 ≤1.30 语义、`min()` 单向夹取）；实现层 UNKNOWN。真机已确认实体存在（53 MB / API 35）与依赖构成 | **[E1]** + **[D]** + **[U]** |

| 5 | 最小替换范围？ | **Kbase + CSF 固件两件套**；用户态**整套保留**；平台层保留 10 / 适配 2 | **[E1]** + **[D]** |
| 6 | gralloc/mapper/HWC/SF 是否有额外约束？ | **有**：HWC/mapper **不链接 DDK**（[D]），但 NEEDED `libged` 覆盖调度/事件面；因 `ged.ko` 不反向依赖 kbase，故障表现为**降级**而非装载失败。SF 则是**一跳强耦合** | **[D]**+[E1] |

### 6.2 一句话总结

> **这次移植的真正边界不在用户态，而在固件。**
> `Kbase + 固件` 是必须成对替换的原子单元；用户态 DDK 是"契约兼容、待实测"的第三块拼图；Android 图形栈与平台层则基本不受影响。
