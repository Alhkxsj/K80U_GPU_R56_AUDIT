# 03_kbase_csf — kbase 内核驱动与 CSF 结构分析

## 目的

对"内核驱动"这条链路做结构测绘与差异分析：R56p0 的 kbase 是什么形状、CSF 路径如何工作、与设备现有 kbase 差在哪里、哪些差异是移植的真正成本。

## 分析对象

| 主题 | 关注点 |
| --- | --- |
| 版本与宏 | `MALI_RELEASE_NAME`、`BASE_KERNEL_VERSION`、CSF 相关编译开关 |
| 设备抽象层 | kbase 如何抽象不同 GPU 后端（CSF vs Job Manager）与不同平台 |
| CSF 队列模型 | 队列组 / 队列、doorbell、固件共享内存、调度与超时处理 |
| 电源与 DVFS | 电源管理回调、时钟/调压耦合点、空闲与挂起流程 |
| 内存管理 | GPU VA 分配、页表、IOMMU 对接点、缓存一致性属性 |
| 与用户态接口 | ioctl / mmap 入口、版本协商（`uk`/`kernel ABI`）机制 |
| 调试与可观测 | trace、debugfs、日志等级（影响可验证性，不是功能项） |

## 产出形式

分析笔记与结构化清单，**不放源码副本**。每份笔记开头声明所依据的树与版本：

```
依据：02_r56_source/mali_r56p0/kernel/... @ R56p0
对照：01_original_baseline/version/kbase_version_*.txt
```

## 目录内文件规划

```
03_kbase_csf/
├── README.md
├── MANIFEST.md
├── architecture/            # 架构测绘：模块划分、初始化顺序、数据结构关系
├── csf/                     # CSF 专属：队列、固件交互、异常恢复
├── abi/                     # 内核↔用户态接口清单与版本协商路径
└── diff_notes/              # 与出厂 kbase 的差异条目（逐条，可追溯）
```

## 准入标准

1. 每条差异条目必须写成可核查的形式：`对象 | 出厂实现 | R56p0 实现 | 差异性质（新增/重构/删除/仅改名） | 影响面`。
2. 涉及行为变化（而非纯重命名）的条目，必须标注**是否影响 ABI 或平台适配**。
3. 引用具体代码时给 `路径:行号`。

## 完成标准

- 能回答：若不改 MTK 平台层，R56p0 kbase 能否编译通过、能否在 G925 MC12 上完成初始化。若不能，卡在哪一层。
- 差异清单按"必须改 / 建议改 / 可忽略"分级完成。

## 与相邻目录的边界

- 本目录处理**驱动通用逻辑**；凡是"MTK 特有"的东西（私有回调、电源域编号、OPP 表、mfgcfg）一律交给 `04_mtk_platform/`。
- 边界判据：**换一块别的 SoC 也成立** → 本目录；**只有 MT6991 成立** → `04`。
- 与用户态的 ABI 结论要回写到 `05_userspace_firmware/`，但接口清单本身在本目录维护。
