## 4. 重要设备事实（防止新 Agent 重复踩坑）

1. **用户已完成三份 Stage 4 设备采集**（`stage4_inventory.txt` / `stage4_file_metadata.txt` / `stage4_elf_analysis.txt`），解析结论已固化在 `05_userspace_firmware/07_device_evidence.md`。**不得要求重新采集这三份文件。**
2. **设备当前运行的是第三方 GKI 内核**，不是原厂 boot。`[D·B]` 结论**不能**写成"原厂环境实测"。
3. `/vendor` 与 `/vendor_dlkm` 下的 GPU 文件与模块属**厂商分区内容**，安装包只写 `boot`（`block=boot` / `do.modules=0` / `do.systemless=0`）**[B]**；但这只说明"该包不改 vendor"，**不证明**设备 vendor 与出厂逐字节一致（U4-27）。
4. **设备 GPU 模块与仓库基线 `.ko` 不是同一构建**：vermagic `6.6.118-…-g57e634f35c1b`（仓库）vs 运行内核 `6.6.143-…-gf9aa2fec23c3`；`ged` 体积 1,093,352 B（仓库）vs 684,032 B（设备，`lsmod` 报值）。
5. 厂商 12 个 GPU 模块**已在第三方 GKI 上实际运行**——这证明 **GKI KMI 未被破坏**，**不代表 R56 已兼容**。
6. 用户当前第三方内核**已稳定使用约一周**——这是**用户提供的背景 [P]**，不是独立实验报告，不可作为稳定性证据引用。
7. 固件的**大小 / SHA256 / strings** 都已取得，但**offset 4/5 的字节未取得**——这三者不能互推。

## 5. 已知技术债与派生影响

### 5.1 固件判据的证据缺口

源码判据（[E1]）与实测判据（[U]）分离：`02_csf_firmware_abi.md` §3 的结论强度是"源码确定 + 推理支持"，不是"字节实测"。任何对外表述必须带这个限定。

### 5.2 用户态契约 ≠ 实现

`03_gles_egl_abi.md` 的全部"兼容"结论都在 UAPI 契约层。`min()` 是**夹取**（取较小值），不是"校验"。DDK 自称版本未知（U4-04）。

### 5.3 最小替换范围

**Kbase + CSF 固件两件套**；用户态**整套保留**；平台层按 Stage 3 保留 10 / 适配 2。影响半径包含 mapper / HWC 的 `libged` 事件面（降级，非崩溃）。

### 5.4 Stage 3 二进制常量的代次错配（**重要**）

`04_mtk_platform/REA_SUPPLEMENT.md` 的 **kCFI 类型哈希**与 **`__versions` CRC** 取自仓库基线 `.ko`（`6.6.118-…g57e634f35c1b`），而设备运行 `6.6.143-…gf9aa2fec23c3`。**这些数值不能直接用于设备**，需按设备构建重导（U4-24）。**源码级结论（依赖方向、调用链、ops 表结构）不受影响。**
