# 06 — ABI 三元组兼容矩阵

> **本文件回答任务书的最终问题**：是否存在 `R56p0 Kbase + 原厂 CSF 固件 + 原厂用户态 DDK` 的可行组合？
>
> **答案**：**不存在**。因为原厂固件被 r56p0 在加载阶段直接拒绝（`header 0.3 ≠ 0.4`）。
>
> **但**存在一个更乐观的替代：`R56p0 Kbase + R56p0 固件 + 原厂用户态`（组合 C）在**契约层是兼容候选**——这比 TASK 03 预期的"用户态也必须换"要轻。
>
> 证据等级：**[E1]** 源码/二进制直接证据 · **[E2]** 交叉推导 · **[E3]** 惯例推断 · **[U]** UNKNOWN

---

## 0. 关键判据回顾（三行决定一切）

| 判据 | 原厂 | R56p0 | 关系 |
| --- | --- | --- | --- |
| **CSF 固件 header minor** | **3** | **4** | **严格 `!=` → 硬阻断** [E1] |
| **CSF UK ABI** | 1.30 | 1.39 | `min()` 协商 → 1.30 用户态得 1.30 语义 [E1] |
| **ioctl / 结构体 / 属性** | — | — | 28/28 逐字相同、30/30 结构体兼容、83/83 属性 ID 不变 [E1] |

> 第一行否决组合 B。第二、三行支撑组合 C。

### 2.2 组合 B — 只换内核（❌ 否决）

| 维度 | 结论 | 等级 |

| UK ABI | 1.30 vs 1.39，`min()` 协商**能通过** | [E1] |

**否决理由（唯一且充分）**：

```c
/* r56p0 csf/mali_kbase_csf_firmware.c:2698 */
if (version_major != FIRMWARE_HEADER_VERSION_MAJOR ||   /* 0 */
    version_minor != FIRMWARE_HEADER_VERSION_MINOR) {   /* 4，而原厂是 3 */
    dev_err(kbdev->dev, "Firmware header version %d.%d not understood\n", ...);
    ret = -EINVAL;
    goto err_out;
}
```

无兼容分支、无白名单、无 fallback。

> **这一条足以终结组合 B**，无需再讨论后续层次。

### 2.3 组合 C — 换内核 + 固件，保留原厂用户态（⚠️ 候选）

这是**最值得关注**的组合，因为它对应"最小替换范围"。

| 维度 | 结论 | 等级 |
| --- | --- | --- |
| **初始化兼容性** | **通过**：`handshake` 取 `min(39,30)=30`，内核以 1.30 语义服务 | **[E1]** |
| **UK ABI** | 1.30 用户态 → 1.30 语义。能力表中 1.31/1.32/1.35 的新能力**全部不生效**，旧行为被完整保留 | **[E1]** |
| **CSF 协议** | 固件 0.4 与内核 r56p0 自洽（官方配套）。**但用户态 1.30 对固件行为的期望**属 **[U]** | [E1]/[U] |
| **GPU 属性查询** | 83 ID 值不变，新增 86/87/88 追加；两阶段 size 协商不越界 | **[E1]** |
| **内存管理** | 12 个 MEM_* ioctl 逐字相同；标志位 CSF 视图 24/24 一致 | **[E1]** |
| **GLES 初始化** | 契约层通过；实际取决于 DDK 是否用被删的 5 个 ioctl、是否清 padding | [E1]/[U] |
| **Vulkan 初始化** | 同 GLES（无独立接口面） | [E2]/[U] |
| **失败表现（若失败）** | 预计为 `-ENOTTY` / `-EINVAL` 类干净错误，而非内存破坏 | [E2] |
| **证据等级** | **[E1]** UAPI 契约 · **[U]** 用户态行为 | — |

#### 2.3.1 为什么说"契约层兼容"是有分量的结论

不是"看起来差不多"，而是六条独立证据：

| # | 证据 | 强度 |
| ---: | --- | --- |
| 1 | 28 个共有 ioctl 的 `_IOW/_IOWR` 三元组**逐字相同**（编号空间未重排） | 强 |
| 2 | 30 个共有结构体**仅 1 个字段改名**（`mem_sync.handle`→`gpu_va`，布局不变） | 强 |
| 3 | CSF 专有 13 个结构体（`cs_queue_register/bind/kick` 等主干）**字段零差异** | 强 |
| 4 | 内存标志位 CSF 视图 **24/24 一致**，bit20/27 两版都标注"JM 专用" | 强 |
| 5 | `gpu_props` **83 个属性 ID 值全部不变**，新增 3 个 ID=86/87/88 **严格追加** | 强 |
| 6 | 能力表**显式为 1.30 保留旧语义**（含 `CSG_CS_USER_PAGE_ALLOCATION` 1.35 门槛，1.30 下走旧路径） | **最强** |

第 6 条是关键：它证明 r56p0 不是"碰巧兼容"，而是**主动设计了兼容窗口**。

#### 2.3.2 组合 C 的真实风险面（不是"能不能启动"，而是"跑起来对不对"）

| 风险 | 描述 | 等级 | 若发生的影响 |
| --- | --- | --- | --- |
| R-C1 | DDK 调用被删的 5 个 ioctl（GWT×3 / HWCNT_SET / DISJOINT_QUERY） | [U] U4-14 | 性能计数功能失效；渲染不受影响 |
| R-C2 | DDK 未清零 padding，`MEM_JIT_INIT` 返回 `-EINVAL` | [U] U4-04 | **tiler heap 不可用 → 渲染可能失败** ⚠️ |
| R-C3 | DDK 严格校验 props 字节数（多 32 字节报错） | [U] U4-15 | GPU 属性查询失败 → 初始化中止 |
| R-C4 | DDK 依赖 `HWCNT` 通知做 DVFS 联动 | [U] U4-16 | 频率策略退化 → 性能下降 |
| R-C5 | 固件 0.4 的默认配置（progress timer 等）与 1.30 DDK 的假设不符 | [U] | 调度行为差异 → 性能/稳定性 |

> **R-C2 是唯一可能"致命"的**。其余都是"功能/性能降级"。

#### 2.3.3 一个被排除的风险

| 曾担心的风险 | 实测结论 |
| --- | --- |
| padding 校验构成新门槛 | **排除**。`check_padding_*` 绝大多数 `return 0`；`MEM_SYNC` 由 Arm **主动替用户态清零**（`mali_kbase_ioctl_helpers.h:157-162` 注释明示） |

## 3. 最小替换范围（核心回答）

### 3.1 结论

> **最小替换范围 = Kbase + CSF 固件（两件套）**。
>
> 用户态 DDK **在契约层可以保留**——这修正了此前"用户态也必须同步替换"的假设。

### 3.2 与 TASK 03 结论的关系

| 阶段 | 结论 | 本阶段的影响 |
| --- | --- | --- |
| TASK 03 | 保留 10 / 适配 2 / 重写 0（针对**平台层**） | 不变 |
| TASK 03-REA | 45 处结构体 + 89 处符号，P3 难度高于预估 | 不变 |
| **TASK 04（本文）** | **用户态可保留**（契约层） | **缩小**了替换范围 |

### 3.3 完整替换清单

| 组件 | 组合 C 是否需要换 | 依据 |
| --- | :---: | --- |

## 4. 为什么"组合 C 不可直接宣布可行"

任务书要求："如果证据不足，必须标记 UNKNOWN，不允许给出肯定结论。"

组合 C 的证据缺口：

| 缺口 | 性质 | 为什么关键 |
| --- | --- | --- |
| 原厂 `libGLES_mali.so` 的实际行为 | **行为证据**（非契约） | 契约兼容 ≠ 实现遵守契约 |
| 固件 0.4 的运行时 GLB 版本 | 固件实体 | 决定 §5 门槛是否真被满足 |
| 1.30 用户态对 0.4 固件行为的期望 | 交叉语义 | 这是唯一"两版都没覆盖"的空白 |

**特别强调第三项**：这是组合 C 的**结构性盲区**。

```
用户态 1.30  ──(UAPI 兼容)──▶  内核 r56p0  ──(同代配套)──▶  固件 0.4
     │                                                          │
     └──────────── 期望的 GPU 行为（未知） ◀────────────────────┘
```

内核在中间做了"语义翻译"，但**固件的实际调度行为**（progress timer 默认值、idle 检测阈值、CSG 抢占策略）由固件自身决定，用户态无法直接约束。若 0.4 改变了这些默认值，1.30 DDK 的性能调优假设可能失效——**表现为性能异常而非功能故障**。

## 5. 决策建议

### 5.1 按风险从低到高排列的验证路径

| 步骤 | 动作 | 目的 | 风险 |
| ---: | --- | --- | --- |
| 1 | **纯静态验证**：采集原厂 `libGLES_mali.so`，`strings` 搜 `1.30`，`readelf` 看依赖 | 确认契约假设 | 无 |
| 2 | **只读设备验证**：`strace -e ioctl` 观察 DDK 实际发的 ioctl 集合 | 确认是否用被删的 5 个 | 无 |
| 3 | **反编译验证**：REA 分析 DDK 的 `MEM_JIT_INIT` 调用点，看是否 memset | 排除 R-C2 | 无 |
| 4 | **构建验证**：r56p0 Kbase + r56p0 固件，在**可恢复环境**中启动 | 验证组合 C 是否成立 | 中（需 fastboot 回滚） |
| 5 | **压力验证**：跑 GFXBench / 游戏，观察帧率与稳定性 | 验证 R-C4/R-C5 | 中 |

> 第 1–3 步全部**只读**，符合本阶段约束，且能排除 3 个风险中的 2 个。

### 5.2 若第 4 步失败，回退方案

| 失败表现 | 可能原因 | 下一步 |
| --- | --- | --- |
| `eglInitialize` 失败 | R-C3（props 校验）或 R-C2 | 反编译定位 |
| 能起但黑屏 | CSF 协议语义不符 | 需 r56p0 DDK（转组合 D） |
| 能起但性能异常 | R-C4/R-C5 | 调固件配置项 |
| bootloop | SurfaceFlinger 强制 GL | 检查 `ro.hardware.egl` |

## 6. 最终回答

### 6.1 任务书六问

| # | 问题 | 答案 | 等级 |
| ---: | --- | --- | --- |
| 1 | 原厂 `libGLES_mali.so` 能否与 R56p0 Kbase 配合？ | **契约层可以**（28/28 ioctl、30/30 结构体、83/83 属性 ID、能力表保留 1.30 语义）；实现层 UNKNOWN | **[E1]** + **[U]** |
| 2 | 原厂 Vulkan ICD 能否配合？ | **无法判定存在性**；若存在则同 GLES 结论 | **[U]** |
| 3 | 原厂 CSF 固件能否直接用于 R56p0？ | **不能**。header 0.3 ≠ 0.4，`-EINVAL` 硬拒绝 | **[E1]** |
| 4 | 是否存在只替换 Kbase、保留用户态和固件的可行组合？ | **不存在**（固件阻断）。但存在"换 Kbase+固件、保留用户态"的候选 | **[E1]** |
| 5 | 最小替换范围？ | **Kbase + CSF 固件两件套**；用户态可保留；平台层按 TASK 03 保留 10/适配 2 | **[E1]** |
| 6 | gralloc/mapper/HWC/SF 是否有额外约束？ | **gralloc/mapper/HWC 免疫**（只依赖 dma-buf）；SF 通过 DDK 间接受影响 | **[E2]/[E3]** |

### 6.2 一句话总结

> **这次移植的真正边界不在用户态，而在固件。**
> `Kbase + 固件` 是必须成对替换的原子单元；用户态 DDK 是"契约兼容、待实测"的第三块拼图；Android 图形栈与平台层则基本不受影响。

### 6.3 证据可信度自评

| 结论 | 可信度 | 理由 |
| --- | --- | --- |
| 组合 B 不可行 | **确定** | 单一代码点，`!=` 硬检查，无分支 |
| 组合 C 契约兼容 | **高** | 六条独立 [E1] 证据互相印证 |
| 组合 C 实测可用 | **未知** | 缺 3 类行为证据 |
| 用户态可保留 | **高（契约）/ 未知（实现）** | 契约完备，实现无证据 |
| Android 栈免疫 | **中高** | dma-buf 通路为 [E1]，HWC 判断为 [E3] |
