# DDK 双路线评估（DDK-A：完整 R56 DDK / DDK-B：R56 Kbase + R49-derived compatibility DDK）

> **本文件做什么**：在同一套证据标准下评估两条用户态 DDK 路线，给出可核验的决策矩阵与推荐。
>
> **版本说明（2026-11-16 第二版，TASK-STAGE4-REMAINDER）**：第一版把备用路线写成"**R46 DDK**"。这是对用户意图的**错误理解**——用户手机的原厂 DDK 是 **R49**，不是 R46。本版按用户的最新路线决策重写：**DDK-B 改为"以原厂 R49 DDK 为基线做深度改造的 compatibility DDK"**。R46 相关内容**不删除**，移入 §4 并标记"已被用户最新路线决策取代"（`D-030`）。
>
> **命名注意**：本文件的 **DDK-A / DDK-B** 指**用户态 DDK 版本选择**，与 [`README.md`](README.md) 中"移植策略 A–D"（整包替换 / 回移 / 仅换固件 / 不移植）是**正交维度**，不可混用编号。两条 DDK 路线都默认搭载在移植策略 **B（以 MTK 为底回移）** 上。
>
> **本文件不做**：不获取、不下载、不反编译、不使用任何来源不明的二进制。全部结论基于仓库内源码与可核验公开资料。

## 0. 结论先行

| 判定 | 结论 | 一句话理由 |
| --- | --- | --- |
| **DDK-A（完整 R56）** | **首选** | 技术上唯一能"完整保留 R56 特性"的路线；缺口是**资产**不是**方案** |
| **DDK-B（R49-derived compatibility DDK）** | **备用，且是有意义的备用** | 与 R46 不同：R49 是**同机、同 SKU、同 release 的配套件**，硬件时间线不矛盾、产品识别已具备；但**改造需要 R49 DDK 源码，而设备上只有编译产物** |
| 两条路线共同前提 | **都必须有 R56p0 的 `mali_csffw.bin`（header 0.4）** | 固件由 **kbase** 加载与校验，与 DDK 版本无关；**DDK 改造不能消除这一约束** |
| DDK-B 的性质 | **必须标注为"兼容移植方案"** | 它不是原生完整 R56 DDK；能否达到"保留 R56 全部特性"取决于改造深度，当前为 [U] |

> **最容易犯的两个错误**：
> ① 把"版本更旧、所以更兼容"当默认假设 —— 更旧意味着**离 R56 更远**；
> ② 把"DDK-B 换版本"当成"绕过固件阻断" —— 固件由 kbase 决定，换 DDK 一点用都没有。

## 1. 三条决定性机制（后面全部结论都从这三条推出）

### 1.1 握手没有下限——任何 `1.x` DDK 都能"成功"

```c
/* mali_kbase_core_linux.c:357-378 */
static int kbase_api_handshake(struct kbase_file *kfile,
                               struct kbase_ioctl_version_check *version)
{
    switch (version->major) {
    case BASE_UK_VERSION_MAJOR:                       /* = 1 */
        version->minor = min_t(int, BASE_UK_VERSION_MINOR, (int)version->minor);
        break;                                        /* ← 取较小者，无下限检查 */
    default:
        version->major = BASE_UK_VERSION_MAJOR;
        version->minor = BASE_UK_VERSION_MINOR;       /* ← 不匹配则回显自己 */
        break;
    }
    err = kbase_file_set_api_version(kfile, version->major, version->minor);
    ...
}
```

| 结论 | 含义 |
| --- | --- |
| **major = 1 是硬要求** | 所有 5th Gen CSF DDK（1.0–1.39）都是 major 1 |
| **minor 无下限** | 1.30 / 1.26 / 1.18 全部握手成功 |
| **"握手成功"零信息量** | 只说明"双方同意用较低版本号"，**不说明任何 ioctl 语义可用** |

### 1.2 能力表把"旧语义"做成显式分支

`kbase_caps_table[]`（`mali_kbase_core_linux.c:145-163`）逐项记录 `required_major/minor`，判定为 `api_version >= required` → **低版本 DDK 得到"不支持"→ 走旧行为**。

以 R49（UK **1.30**）为 `api_version` 时的落点：

| cap | required | 1.30 下 |
| --- | ---: | --- |
| `SYSTEM_MONITOR` / `JIT_PRESSURE_LIMIT` | 1.0 | ✅ 支持 |
| `QUERY_MEM_DONT_NEED` | 1.22 | ✅ |
| `QUERY_MEM_SAME_VA` | 1.28 | ✅ |
| `REJECT_ALLOC_MEM_DONT_NEED` / `_PROTECTED_IN_UNPROTECTED_ALLOCS` / `_UNUSED_BIT_20` / `_UNUSED_BIT_27` | 1.31 | ❌ 走旧行为 |
| `REJECT_ALLOC_MEM_UNUSED_BIT_5` / `_BIT_7` | 1.32 | ❌ |
| `CSG_CS_USER_PAGE_ALLOCATION` | 1.35 | ❌ 走"CSG 自己分配 user page"旧路径 |

| 结论 | 含义 |
| --- | --- |
| **R56 kbase 保留 1.0 起的旧语义路径** | 不是"只支持 1.39"，是"按 DDK 声称的版本降级" |
| **这是 R49 DDK（1.30）能在 R56 kbase 上工作的机制性原因** | 不是巧合 |
| **同时也是"R56 新特性会全部失效"的机制性原因** | 只要 DDK 声称 1.30，kbase 就**不会**给它 1.31+ 的能力 |

> **关键推论（对本路线评价最重要的一条）**：R49-derived DDK **原样运行**在 R56 kbase 上时，行为与"组合 C"完全相同 —— **特性保留度 = 1.30 语义**。要让 R56 新特性生效，DDK 必须**真的改成**声称并实现更高 UK 版本，而这需要 **DDK 源码**。

### 1.3 ioctl 用"同一请求号 + 不同 size"做版本化

```c
#define KBASE_IOCTL_CS_QUEUE_GROUP_CREATE_1_6   _IOWR(KBASE_IOCTL_TYPE, 42, …_1_6)    /* 32 B */
#define KBASE_IOCTL_CS_QUEUE_GROUP_CREATE_1_18  _IOWR(KBASE_IOCTL_TYPE, 58, …_1_18)   /* 40 B */
#define KBASE_IOCTL_CS_QUEUE_GROUP_CREATE_1_35  _IOWR(KBASE_IOCTL_TYPE, 58, …_1_35)   /* 112 B */
#define KBASE_IOCTL_CS_QUEUE_GROUP_CREATE       _IOWR(KBASE_IOCTL_TYPE, 63, …)        /* 120 B */
```

`switch (cmd)` 按**完整请求号（含 size）**分派 → size 不同即不同分支；未登记的 size → `-ENOTTY`。

| 结论 | 含义 |
| --- | --- |
| 向后兼容的粒度是**结构体大小**，不是版本号 | 同一 minor 段的多次扩展靠 size 区分 |
| **R49（nr 58 / 112 B）精确命中 R56 的 `_1_35`** | `05/09` §11.1 已验证；且 `_1_35` 的处理函数做**逐字段迁移**（`mali_kbase_core_linux.c:1446-1472`） |
| 这是 R49 DDK 能在 R56 kbase 上工作的**第二个**机制性原因 | 与 §1.2 并列 |

## 2. 路线 A：完整 R56 DDK

### 2.1 需要什么

| 组件 | 内容 | 现状 |
| --- | --- | --- |
| Kbase | `AX504X08X-SW-99002-r56p0-18eac0.tar.gz`（MD5 `62b168823691eb61ec29654cbf35e719`） | ✅ **在手**（`02_r56_source/`） |

### 2.2 技术可行性（假设资产到位）

| 检查项 | 判定 | 依据 |
| --- | --- | --- |
| kbase ↔ DDK 的 UK ABI | **同代 1.39 对 1.39** | 同一 release 交付 |
| GLES/EGL/Vulkan 完整性 | **完整** | 商业 DDK 定义 |
| G925 MC12 支持 | **有** —— `GPU_ID_PRODUCT_TKRX` + `tKRx` workaround 表 | `mali_kbase_hw.c:272`、`mali_kbase_core_linux.c:2583` |

| MTK 私有接口 | **需重建连接层**（保留 10 / 适配 2） | `04/06` §1 |
| **R56 新特性** | **可全保**（DDK 同代） | — |

### 2.3 唯一缺口：资产与授权

| 问题 | 答案 |
| --- | --- |
| 源码包里有没有固件/DDK | **没有**。23 条目，`firmware`/`.bin`/`ddk`/`libGLES`/`vulkan`/`csffw` 命中全为 0 [E1] |
| 有没有公开合法渠道 | **没有**。Arm 的 DDK 与 CSF 固件属**商业授权交付件** |
| 能否用别的机型的 R56 DDK | **不可以**。DDK 是 per-GPU 产品配置编译的；跨机型 = 未经验证组合 |
| 能否改 R49 固件的 header 冒充 0.4 | **禁止**。header 只是入口校验，entry 表随 release 变化 |

> **DDK-A 的状态是"方案成立、资产缺失"，不是"技术不可行"。**

## 3. 路线 B：R56 Kbase + R49-derived compatibility DDK

### 3.1 先纠正路线定义

| 维度 | **R46 路线（第一版，已废弃）** | **R49 路线（本版）** |
| --- | --- | --- |
| 与目标机的关系 | **无关机型**：G925 发布 2024-05-29，R46 ≤ 2024-02，其 workaround 表不可能含 `tKRx` | **同机配套**：R49 就是这台手机出厂运行的 DDK，`tKRx` 支持完整（features 完全相同，issues 差 3 项） |
| 产品识别 | 大概率无 G925 MC12 配置 | **已验证在跑 G925 MC12**（设备就是证据） |
| CSG 结构体落点 | 未知，可能 `-ENOTTY` | **已知**：nr 58 / 112 B，精确命中 `_1_35` |
| 资产来源 | 本机**完全没有** R46 资产 | **本机有 R49 的编译产物**（`libGLES_mali.so` 53 MB，`r49p1-03bet0`）；源码需另取 |
| 保留 R56 特性 | 不可能（跨代，且是向下跨两代） | **可能**，但取决于改造深度 + 是否有源码 |

> **一句话**：用户把备用路线从 R46 改成 R49 是**方向性正确**的——R49 在本平台**已经被证明能驱动这颗 GPU**，而 R46 从未在此平台出现过。第一版报告用一个"时间线矛盾"把备用路线整体否掉，是**把 R49 与 R46 混为一谈**造成的误判。

### 3.2 R49 DDK 资产的真实形态（这是整条路线的关键约束）

| 资产 | 是否在设备上 | 证据 |
| --- | --- | --- |
| `libGLES_mali.so` **编译产物** | ✅ 在（53,105,232 B，Build ID `700e6d4112a6a8a5`），含 `r49p1-03bet0` | [D·A] `05/07` §5.1、§5.4 |
| `vulkan.mali.so` 薄壳编译产物 | ✅ 在（133,416 B） | [D·A] |
| **R49 DDK 源码** | ❌ **不在**。设备不会有源码；仓库 `01_original_baseline/` 只有 **kbase 内核驱动源码**（`mali-r49p1/…/drivers/gpu/arm/midgard/`），**没有** `libGLES_mali.so` 的源码 | [E1] 目录全量枚举 |
| R49 CSF 固件 | ✅ 在（header **0.3**，307,200 B） | [D·A] |

> **必须说清的一句话**：**"从手机提取 R49 DDK 源码"这件事不成立。** 手机提供的是编译产物；源码只能来自 Arm / MTK 的授权交付。因此 DDK-B 的可行形态只有两种：

| 形态 | 前提 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| **B1：有源码** | 从 Arm/MTK 取得 `r49p1-03bet0` 的 DDK 源码包 | 在源码层改 UK 版本、改 CSG 结构、改 props 协商、改 ioctl 调用面 —— **这条路才是"深度改造"** | 仍然不能消除固件 header 0.4 的约束 |
| **B2：只有二进制** | 仅设备上的 `.so` | 只能**原样运行**（= 早前 Stage 的"组合 C"） | 不能改任何行为；不能"保留 R56 新特性"；二进制补丁属未验证且不可维护，本项目**不予推荐** |

**所以路线 B 的准入门槛是同一句话**：有没有 R49 **DDK 源码**。这一点与路线 A 的"有没有 R56 DDK"形式相同，但**概率不同**——见 §3.3。

### 3.3 为什么路线 B 仍然值得保留（而不是"同样被阻断所以没意义"）

| 论点 | 内容 | 等级 |
| --- | --- | --- |
| ① **资产可得性可能更好** | 整机出厂就用 R49 DDK。SoC 厂商（MTK）的 BSP / 授权包里**通常带有当期 DDK 源码**，因为整机厂要基于它集成。而 R56 DDK 是**更新的、需要单独向 Arm 申请**的版本 | **[E3]** 惯例推断，未验证 |
| ② **改造是增量而非新建** | 若拿到 R49 源码，起点就是"这台手机真实在跑的代码"，MTK 的平台补丁、GED/GPUD 对接、`arm.mali.platform` AIDL 适配**全都在里面**；而 R56 DDK 需要把这些**重做一遍** | **[E2]** 由平台层审计推导 |
| ③ **硬件支持零缺口** | R49 的 `tKRx` features 与 R56 **完全相同**，issues 只差 3 项且都在 kbase 侧 → DDK 侧不需要为 G925 补任何硬件适配 | **[E1]** |
| ④ **回滚面小** | 改造后的 DDK 若失败，可退回原厂 DDK + 原厂 kbase（完整原厂栈） | [E1] 结构性 |

> **但必须同时承认**：以上四条**没有一条**能证明"改造后能与 R56 kbase 协同"。这是**待验证的方案**，不是**已验证的结论**。

### 3.4 固件约束不因 DDK 改造而消失（必须单独解决）

| 事实 | 值 | 等级 |
| --- | --- | --- |
| 原厂固件 header | **0.3** | [D·A] 字节实测 |
| R56 kbase 要求 | **0.4**，`!=` 严格、无 fallback | [E1] `csf/mali_kbase_csf_firmware.c:85-86, 2698-2701` |
| 结论 | **B1 / B2 两种形态都需要一份 header 0.4、G925 MC12 的 R56 固件** | [E1]+[D·A] |

> **不得假设**"R49 固件可以配 R56 的改造 DDK"。固件由 kbase 加载并校验，kbase 一旦换成 R56，固件就必须是 0.4。**DDK 侧的任何改造都不改变这条**。
>
> 也因此："先用 R49 改造 DDK 顶着、以后再解决固件"这个顺序**在技术上不成立**——没有 0.4 固件，R56 kbase 连 `open()` 都过不去，DDK 改造完也无处可跑。**固件必须与 DDK 同时到位，或者先到位。**

### 3.5 R49 改造能触及的边界（详细版见 `R49_DDK_ADAPTATION_PLAN.md`）

| 层面 | 可否由 R49 改造覆盖 | 说明 |
| --- | --- | --- |
| UK ABI 版本号（1.30 → 1.39） | **可以**（改 `BASE_UK_VERSION_MINOR` 与握手指令） | 但**改了版本号不等于实现了语义**——kbase 会按 1.39 给能力，DDK 必须真的用起来，否则是"谎报版本"（`AGENTS.md` 禁止项） |
| CSG create 结构体（112 → 120 B） | **可以** | 需迁移 `neural_mask` / `comp_pri_*` / `fragment_endpoint_task_limit` / `reserved` |
| GPU props 协商 | **可以** | 必须做 `size=0` 两步探测（R56 缓冲区 **781 B** > R49 的 **749 B**） |
| padding 清零 | **可以**（且多半本来就有） | 3 项已被设备行为证明；`CS_QUEUE_REGISTER` 等 4–8 项需在源码里确认 |
| 内存管理 / JIT / dma-buf / MGM / PMA | **部分可以** | UAPI 结构体 51 个实质差异 0，故主要是行为对齐，不是接口重写 |
| MTK GED / GPUD / GPUFreq 私有对接 | **可以**（且是 R49 的既有优势） | `libged`/`libgpud` 的调用约定在 R49 DDK 里已存在 |
| ioctl 55 / 80 的缺失 | **可以改为不调用** | 55 在 CSF 上本就是 no-op；80 需自行实现超时上报或放弃 MTK 自愈入口 |
| **R56 新特性（1.31–1.39）** | **取决于源码可得性** | 无源码 → 不可能；有源码 → 需逐项实现，工作量未知 |
| **CSF 固件 header 0.4** | **完全不能** | 只能取得 |

## 4. 历史记录：R46 路线（**已被用户最新路线决策取代**，不删除）

> **状态**：`已被取代`（`D-030`）。保留本节是为了让后续 Agent 知道"曾经评估过 R46、为什么被换掉"，**不得**据此恢复 R46 评估。

第一版（`bbaeaf2`）把备用路线写成"R56 Kbase + R46 DDK"，并给出三条否决理由。**三条理由对 R46 本身仍然成立**，但它们**不能用于评价 R49**：

| 第一版理由 | 对 R46 | 对 R49 |
| --- | --- | --- |
| ① 不解除固件阻断 | ✅ 成立 | ✅ **同样成立**（这是两条路线的共同前提，不是 R46 特有缺点） |
| ② 硬件时间线矛盾（G925 晚于 R46 ≥4 个月） | ✅ 成立（[E2]） | ❌ **不成立**——R49 就是出厂件，`tKRx` features 与 R56 完全相同 |
| ③ CSG size 落点未知，可能 `-ENOTTY` | ✅ 成立（R46 未验证） | ❌ **不成立**——已知为 nr 58 / 112 B，精确命中 `_1_35` |

**第一版的真正错误**：把 ②③（R46 特有）当成了"所有非 R56 DDK"的通病，从而把用户提出的备用路线整体否掉。**②③ 是 R46 的缺点，不是"降级路线"的缺点。**

> 若日后确有 R46 交付物，仍按原文判据检验：`mali_kbase_hw.c` 是否含 `GPU_ID_PRODUCT_TKRX`、CSG create size 是否 ∈ {40, 112, 120}。本节结论**不因此改变**——R46 仍不是本项目的备用路线。

## 5. 决策矩阵

| # | 评估项目 | **DDK-A：完整 R56 DDK** | **DDK-B：R49-derived compatibility DDK** |
| ---: | --- | --- | --- |
| 1 | **获取可能性** | Arm 商业交付（随 SoC 授权包）；**未见于本机任何位置** | 编译产物**本机已有**；源码需授权，但**可能随 MTK BSP 一并提供**（[E3]） |
| 2 | **源码可改造程度** | 不需改造（同代） | **有源码 → 高**；**只有二进制 → 零**（不可改造）。当前源码状态 **BLOCKED** |
| 3 | **UK ABI 兼容性** | 1.39 ↔ 1.39，**同代无风险** | 1.30 ↔ 1.39：握手必过（§1.1）、caps 按 1.30 降级（§1.2）→ **能跑，但拿不到新能力** |
| 4 | **CSF ioctl 与结构体** | 完全匹配 | 51 个共同结构体实质差异 0；CSG 112→120 被 `_1_35` 吸收；**R56 删 6 个 ioctl**（55/80 为生产相关项）→ 需改造调用面 |
| 5 | **padding 规则** | 天然满足 | **3/15 已被设备行为证明满足**；`CS_QUEUE_REGISTER` 等 4 项致命位**待证**（`STAGE4_REMAINING_AUDIT` §3.1） |
| 6 | **GPU properties** | 86 个 ID，781 B | R49 为 83 个 ID、749 B；**新增 3 个（+32 B）**，须做 `size=0` 两步协商，否则 `-EINVAL` |
| 7 | **内存管理（JIT / dma-buf / MGM / PMA）** | 与 R56 kbase 同代 | 结构体无实质差异；MGM/PMA 是 MTK 侧模块（保留 10 / 适配 2），**与 DDK 版本无关** |
| 8 | **MTK GED / GPUD / GPUFreq / MGM / PMA 私有接口** | **需重建连接层** | **R49 源码里已存在**（这是本路线最大优势之一，[E2]） |
| 9 | **GLES / EGL / Vulkan** | 官方整套，UK 1.39 | 原厂整套（`libGLES_mali.so` + `vulkan.mali.so` 薄壳 + 4 个 MTK 私有 gralloc 库）；改造需**整套重编**，不能拆 |
| 10 | **CSF 固件** | 需 header 0.4 + G925 MC12 | **同样需 0.4** —— 由 kbase 决定，**DDK 改造无法消除** |
| 11 | **R56 新特性保留程度** | **100%** | 原样运行 = **1.30 语义（新特性全失）**；有源码改造 → 逐项实现，**当前 [U]** |
| 12 | **维护成本** | 低（与上游同代，跟着 release 走） | **高**（自维护一条改造分支；每次 R56 kbase 升级都要重新对齐） |
| 13 | **风险性质** | 资产风险（拿不到就没有） | 工程风险（拿得到也可能改不完）+ 资产风险（源码） |
| 14 | **失败时的退路** | 退回原厂 R49 整套 | 退回原厂 R49 整套（同一退路） |
| 15 | **当前可行性** | **技术可行 / 资产阻断** | **方案存在 / 源码阻断 / 效果未验证** |

> **矩阵读法**：第 1 行与第 10 行决定"能不能开始"，第 11 行与第 12 行决定"值不值得做"。

## 6. 推荐决策

### 6.1 结论

> **优先 DDK-A（完整 R56）。若 R56 DDK 确认不可获得、而 R49 DDK 源码可获得，则转 DDK-B，并接受"这是兼容移植方案，不是原生完整 R56"。**
>
> **两条路线都必须单独解决 R56 CSF 固件（header 0.4 / G925 MC12）。固件是共同的、不可绕过的硬前置。**

### 6.2 两条路线的关系（不是二选一，是先后）

| 情形 | 选择 |
| --- | --- |
| R56 DDK 可得 | **选 A**，不做 B |
| R56 DDK 不可得、R49 源码可得 | 选 B，**明确标注为兼容移植**，并把"特性保留度"作为独立验收项 |
| 两者都不可得 | **不启动 Stage 5B**；只能做"原样运行"（组合 C）并接受 1.30 语义 |
| 只有 R49 二进制、无任何源码 | **等价于组合 C**，不构成"改造" |

### 6.3 会重启 DDK-B 正式评估的条件

| # | 触发条件 |
| ---: | --- |
| 1 | R56 DDK **确认不可获得**（有书面结论，不是"没找到"） |
| 2 | 且 **R49 DDK 源码**可获得（版本需匹配 `r49p1-03bet0`，或其可直接对应的 tag） |
| 3 | 且 已取得 header 0.4 / G925 MC12 的 R56 固件（否则改造完也跑不起来） |
| 4 | 且 用户书面接受"可能无法保留全部 R56 特性" |

> 四条**同时**满足才值得投入。当前满足 **0 条**。

### 6.4 不能说的话

| 禁止表述 | 原因 |
| --- | --- |
| "R49 改造后就是完整 R56 DDK" | 没有证据；且 §1.2 说明"声称 1.30 就只得到 1.30" |
| "R49 DDK 一定清零 padding，因为设备能跑" | **部分成立**（3 项已证），但 `CS_QUEUE_REGISTER` 等 R49 完全不查，设备能跑**不能**反推 |
| "握手成功就说明 DDK 可用" | §1.1，握手零信息量 |
| "先改 DDK，固件以后再解决" | §3.4，没有 0.4 固件 R56 kbase 连 `open()` 都过不去 |
| "R49 固件改 8 字节 header 就能给 R56 用" | entry 表随 release 变化，改 header 只会把早失败变成晚崩溃 |
| "R46 与 R56 版本接近所以兼容"（历史） | 见 §4；R46 不是本项目路线 |
