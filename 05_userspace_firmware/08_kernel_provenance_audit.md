# 08 — 第三方 GKI 环境下的设备证据来源审计

> **本文件回答什么**：Stage 4 的全部"真机实测"结论，究竟来自**原厂环境**还是**第三方内核环境**？厂商文件、运行时状态、内核模块这三类证据能否分开？分开之后，哪些结论仍然成立、哪些必须降级？
>
> **一句话结论**：设备当前运行的是**第三方 GKI 内核**（KernelSU 补丁，内核源码提交 `f9aa2fec`），而 `/vendor` 下的 GPU 文件与 `/vendor_dlkm` 下的 GPU 模块属于**厂商分区内容**，未被该安装包改动。因此 **Stage 4 的实测证据是"厂商分区 + 第三方内核"的混合环境**，此前一律记作"真机实测 / 出厂状态"是**口径错误**；本次按 A/B/C 三类拆分并重标。
>
> **本文件不做**：不重跑 Stage 1–4，不刷机，不替换驱动，不做移植设计，不进入 Stage 5。

## 0. 摘要

### 0.1 证据等级扩展（本轮新增两级）

| 级别 | 含义 | 可反驳性 |
| --- | --- | --- |
| **[D]** | 设备实测（本轮起细分为 `[D·A]` / `[D·B]` / `[D·C]`，见 §2.1） | 只能被"采集脚本写错"推翻 |
| **[B]** | **构建记录**：公开可核验的 CI 运行页、产物清单、构建模板源码 | 只能被"看错行"推翻；**不等于设备实测** |
| **[P]** | **用户声明**：任务书或对话中给出、但本次无法独立复核的参数 | 可被构建记录推翻 |
| **[E1]** | 源码 / 二进制直接证据（仓库内文件，行号级） | 可被版本误认推翻 |
| **[E2]** | 交叉推导（≥2 条 [D]/[B]/[E1]） | 可被新证据推翻 |
| **[E3]** | 惯例推断（AOSP / Android 通用实现） | 最弱，仅作方向 |
| **[U]** | UNKNOWN | — |

> 为什么要加 [B] 与 [P]：本轮的核心发现是**"设备实测"与"构建记录"必须分开**。CI 页面能证明"这次构建打了什么补丁、产出什么包"，**不能**证明"设备上跑的就是这个包"。混用这两者，正是上一轮把"原厂环境"写错的方法论根源。

### 0.2 一页结论

| 问题 | 结论 | 等级 |
| --- | --- | --- |

### 1.3 安装脚本的实际参数

AnyKernel3 模板来自 `WildKernels/AnyKernel3` 分支 `gki-2.0`，其 `anykernel.sh` 的原文参数：

```sh
do.devicecheck=0
do.modules=0
do.systemless=0
do.cleanup=1
do.cleanuponabort=0
do.check_boot_version=0
...
block=boot
is_slot_device=auto
ramdisk_compression=auto
patch_vbmeta_flag=auto
```

安装流程（同一文件）：

```sh
split_boot
if [ -f "$SPLITIMG/ramdisk.cpio" ]; then
  unpack_ramdisk
  write_boot      # 仅重写 boot 分区
else
  flash_boot
fi
```

| 参数 | 取值 | 对来源归属的意义 |
| --- | --- | --- |
| `block=boot` | **boot** | 只处理 `boot` 分区；`init_boot` / `vendor_boot` / `dtbo` 不参与 |
| `do.modules=0` | 关 | **不安装任何 `.ko`**，即使包内有也不会写入 |
| `do.systemless=0` | 关 | 不做 systemless 覆盖（不往 `/system`、`/vendor` 注入） |
| `patch_vbmeta_flag=auto` | 自动 | 可能改写 **vbmeta 验证标志**（属 boot 侧验证链），**不改分区内容** |
| `do.check_boot_version=0` | 关 | 不校验 boot 版本，允许跨 ROM 刷入 |

### 1.4 安装范围结论

| 动作 | 是否发生 | 依据 |
| --- | :---: | --- |
| 写 `boot` 分区 | **是** | `block=boot` + `write_boot` |
| 写 `init_boot` / `vendor_boot` / `dtbo` | 否 | 脚本无对应路径 |
| 写 `vendor` | **否** | 脚本无 `vendor` 路径；`do.systemless=0` |
| 写 `vendor_dlkm` | **否** | 同上；且 `do.modules=0` |
| 安装内核模块 `.ko` | **否** | `do.modules=0`；产物无 modules |
| 安装 CSF 固件 | **否** | 产物无 `.bin` |
| 安装 GPU 用户态库 | **否** | 产物无 `.so`；APK 单独安装 |
| 改 AVB 验证标志 | 可能 | `patch_vbmeta_flag=auto` |

佐证（`[D·A]`）：设备属性 `ro.vendor.build.ab_ota_partitions` 明确列出 `boot`、`init_boot`、`vendor_boot`、`vendor`、`vendor_dlkm`、`dtbo` 为**彼此独立的分区**。仅写 `boot` 不会波及其余分区。

### 1.5 这个结论不能推出什么

| 不能推出 | 原因 |
| --- | --- |
| "设备全部文件与出厂一致" | 只证明**本次安装**未改 vendor；不覆盖 OTA 升级、其他模块（Magisk / KSU 元模块）、用户手工改动 |
| "`/vendor` 内容未被任何机制覆盖" | `NoMount-Metamodule` 是**可选**安装项，具备 overlay 挂载能力；采集未记录 mount 表（U4-27） |
| "内核是原厂内核" | 恰恰相反：`u:r:ksu:s0` 证明内核已被 KernelSU 补丁化 |
| "第三方内核改动面仅限 KernelSU" | 同一构建还启用了调度/调频等补丁（§4） |

## 2. 三类设备证据分类

### 2.1 分类规则

| 类别 | 定义 | 标签 | 判据来源 |
| --- | --- | --- | --- |
| **A. 厂商分区静态文件** | `/vendor`、`/system` 等**只读分区**上的文件，由厂商 ROM 提供，本次安装未改动 | `[D·A]` | 路径 + 大小 + SHA256 + ELF 头 |
| **B. 第三方 GKI 运行时状态** | 由**当前运行内核**产生的状态：`uname`、`lsmod`、`/sys/module`、`/dev/mali0`、服务 pid、getprop、DT | `[D·B]` | 运行时命令输出 |
| **C. 厂商内核模块** | `/vendor_dlkm` 提供的 `.ko`，**文件属厂商、装载于第三方内核** | `[D·C]` | `lsmod` + `/sys/module/*/version` + 文件元数据 |

> **B 与 C 的关系是本文件的核心**：C 是**文件**（厂商来源），B 是**状态**（第三方来源）。同一个 `modprobe` 事件同时产生 C 的"存在"与 B 的"已装载"，但**来源归属相反**。把它写成"原厂内核已装载原厂模块"就把两件事合并了。

> 1. **设备侧 GPU 相关文件是 18 个，不是 15 个**。仓库 15 = 12 GPU + 3 MET；设备 18 = 15 个两侧共有 + **3 个仓库没有**（`mtk_ghpm`、`mtk_cg_peak_power_throttling`、`mtk_smmu_qos`）。因此"仓库 15 个对应设备 15 个"的说法不成立，**集合本身不对称**，且不对称方向是"设备多"。
> 2. **`met_*` 三模块"文件存在、未装载"已确认**。全量 `/proc/modules`（597 个）中确无它们，不再是"筛选口径下未见"。它们由 `met.ko` 按需加载，本机 MET 未启用。

**C 类能证明**：厂商模块在该第三方内核上**装载成功**；13 个 GPU 链路模块的身份、大小、哈希、版本串均已实测。

## 3. GPU 模块来源核验

### 3.1 决定性判据：不是两个版本，是三个

> **2026-11-16 00:04 实测更正**：本节前一版只列了两个串（仓库 `6.6.118-…-g57e634f35c1b` 与运行内核 `6.6.143-…-gf9aa2fec23c3`），据此断言"`modversions` 下必须逐字符相等，所以设备 `.ko` 必然是另一次构建"。**推理的方向没错，但前提少了一个串。** 设备 `.ko` 的 `.modinfo` 实测为 `6.6.118-android15-8-g54a15cf3acba-4k`——它既不是仓库那份，也不是运行内核那份。

| 序 | 对象 | vermagic / 版本串 | 来源 | 等级 |
| ---: | --- | --- | --- | --- |
| ① | **仓库基线 15 个 `.ko`** | `6.6.118-android15-8-**g57e634f35c1b**-4k SMP preempt mod_unload modversions aarch64` | `01_original_baseline/`，抽取自 **OS3.0.305.0.WONCNXM** | **[E1]** |
| ② | **设备 18 个厂商 `.ko`** | `6.6.118-android15-8-**g54a15cf3acba**-4k SMP preempt mod_unload modversions aarch64` | 设备 `/vendor_dlkm/lib/modules/`，`.modinfo` 逐文件实测 | **[D·A]** |
| ③ | **设备运行内核** | `6.6.143-android15-8-**gf9aa2fec23c3**-4k` | `uname -r`，SukiSU-Ultra 第三方构建 | **[D·B]** |

**三者互不相等**（①②同 sublevel 不同提交；③连 sublevel 都不同）。

#### 3.1.1 为什么②可以代表"原厂 boot 的内核"

设备上的 `/vendor_dlkm` 不是本次安装写入的——安装器参数为 `block=boot`、`do.modules=0`、`do.systemless=0`（§1.3/§1.4），产物中也不含任何 `.ko`。因此②是**厂商 OTA 原样内容**。

在原厂环境下，`same_magic()` 对 `modversions` 内核做逐字符比较，不符即 `-ENOEXEC`。②能被原厂内核接受，说明**原厂 boot 的 `VERMAGIC_STRING` 与②相等**。

> 等级 **[E2]**：这是推理，不是读数。我们没有原厂 boot 分区，也没有它的 `uname -r`。**能够确定的是"厂商模块的构建基线 = ②"，能够推断的是"原厂 boot 的内核串 = ②"。** 前者 **[D·A]**，后者 **[E2]**。

#### 3.1.2 这条更正推翻了什么

> **项目自 Stage 1 起把 `6.6.143` 记作"设备内核 / 出厂内核"，这是错的。**
>
> `6.6.143-android15-8-gf9aa2fec23c3-4k` 是**第三方内核**（SukiSU-Ultra，构建者 `chandr1000@SukiSU-Ultra-v41181`，基于 GKI `android15-6.6` sublevel 143）。
> **原厂 boot 的内核应为 `6.6.118-android15-8-g54a15cf3acba-4k`**（由厂商模块 vermagic 反推，[E2]）。
>
> 影响面：根 `README`、`AGENTS.md` §0、`03_kbase_csf/06`、`04_mtk_platform/01` 中"设备 6.6.143"的表述均已按三层版本改写；`01_original_baseline/source_integrity.md` 的 U1（"目标机当前内核是否真为 6.6.118"）由开放改为**闭合**（追加注记，正文不改）。
>
> **技术结论未变**：仓库基线 `.ko` 与设备 `.ko` 仍不同源；Stage 3 的二进制常量仍不可直接用于设备。变的是**理由**——不是"118 vs 143"，而是"同为 6.6.118 分支、不同 git 提交"。

### 3.2 辅助判据：文件大小与节大小（**"同大小"不等于"同文件"**）

拿到设备文件后，上一版基于 `lsmod` 内存尺寸的对比已作废。真实数据如下（完整表见 §3.7.1）：

| 判据 | 仓库（OS3.0.305.0） | 设备（OS4.0.3.0） | 结论 |
| --- | --- | --- | --- |
| `ged.ko` 文件大小 | 1,093,352 B | **1,093,352 B** | **完全相同** |
| `ged.ko` SHA256 | `f53e8c6833e82d8f…` | `e4ff2a35e3019a97…` | **不同** |
| `ged.ko` `.text` 节 | `0x033c10` | `0x033c10` | 相同 |
| `ged.ko` `__versions` 节 | `0x003c40` | `0x003c40` | 相同 |

> **这是本轮最容易写错的一处。** 上一版把 `lsmod` 的 684,032 B 当作"设备文件大小"，得出"差 409 KB"。实测证明：设备 `ged.ko` 与仓库 `ged.ko` **字节数一模一样**，`lsmod` 那个数是 `core_layout.size`（页对齐内存），见 §3.6.2。
>
> 但**"大小相同"绝不能读成"同一文件"**：两者的 vermagic 串不同（`g57e634f35c1b` vs `g54a15cf3acba`，恰好等长 12 字符），这一处替换不改变文件长度，却足以让 SHA256 全变。
>
> 正确用法：大小与节大小相同 → **差异面被压缩到极小**（大概率只有 vermagic 与少量构建元数据）；**不是**"同一二进制"，也**不是**"ABI 等价"。

#### 3.2.1 时间戳仍不可作判据

`uname -v` 为 `Mon Oct 5 04:20:00 UTC 2026`，而构建运行 #11 发生在 11-14。这**不能**推出"设备没刷这个包"，也**不能**推出"刷了"——GKI 可复现构建常固定 `KBUILD_BUILD_TIMESTAMP`，且同配置的多次构建会产生同一串。因此"设备上的内核是否为 run #11 的字节"仍记 **U4-26**（[U]），不是结论。

### 3.4 对 TASK 03 数值结论的影响（**重导范围已收窄**）

Stage 3 / 03-REA 的**二进制级数字**是在仓库基线那批 `.ko`（OS3.0.305.0 / `g57e634f35c1b`）上测的。实测对照后，重导负担按"模块是否实质变化"分层：

| 结论类型 | 示例 | 是否受影响 | 处理 |
| --- | --- | :---: | --- |
| 源码级结构（函数指针表项数、成员顺序） | `gpufreq_fp` 416 B / 52 项、MGM ops 72 B | 低 | 保留 |
| 符号计数与依赖方向 | kbase→MTK 89 处、GED 导出 168、无外部引用 114 | 低（源码级） | 保留 |
| **kbase 的 `__versions` CRC** | 514 条 → 设备 513 条 | **高** | 必须重导（U4-24b） |
| **kbase 的 kCFI 类型哈希** | `.text` 差 6,788 B | **高** | 必须重新取得 oracle |
| **其余 14 个模块的 `__versions` CRC** | 节大小逐字节相等 | **低**（结构性一致） | 可沿用；若要严格，用一次 `readelf -x` 比对（§3.7.6） |
| 模块大小 / 段布局 | `ged` 1,093,352 B（**两侧相同**） | 无 | 已按 §3.2 更正 |

> **这就是本任务最大的工程收益**：上一版说"kCFI 与 CRC 必须在设备构建上重导"，等于把 15 个模块全算一遍。实测把范围压到 **kbase 一个模块**——因为其余 14 个的 `.text` 与 `__versions` 节大小在两侧逐一相等，其中 `mali_mgm` 与 `mali_prot_alloc` 的 `srcversion` 更是**逐字符相同**（§3.7.3）。

### 3.5 一个正向副产物：KMI 兼容性已被实机证明（**但证据力比原以为的弱**）

厂商 GPU 模块能在**重新编译的** `6.6.143` GKI 内核上装载并正常工作。上一版据此认为"该内核保留了 GKI KMI（`android15-8`）的导出符号与 CRC"。**实测后必须补一句限定**：这些模块的 vermagic 明确写着 `6.6.118-g54a15cf3acba`，与运行内核 `6.6.143-gf9aa2fec23c3` 不符，**本应被 `same_magic()` 拒绝却装载成功** → 该内核**绕过了 vermagic 检查**（§3.7.4）。

因此：

1. "装载成功"证明的是"**该内核愿意接受不匹配模块**"，不证明"符号 CRC 也匹配"（`check_version` 是否同样被绕过，见 §3.7.4 的两分支）；
2. "换内核"这条路在**模块装载层面**是通的——这条仍然成立，但**通的原因部分来自补丁，而非 ABI 兼容**；
3. 这**不构成** r56p0 的兼容性证据。r56p0 kbase 需要的是 MTK 模块导出的那 89 个符号及其 CRC 与自身引用匹配（TASK 03 已证反向依赖为 0），这与"GKI 导出集未变"是两件事。

> **工程警告（新增）**：在任何"打了 vermagic 绕过的内核"上做 Stage 5 验证，"能装载 / 能跑"都**不能**作为 ABI 兼容的证据。这类环境会把不匹配掩盖成正常。

### 3.6 U4-24：模块身份核验的口径、判定矩阵与"哪些常量必须重导"

> 本节是 U4-24 的**方法学与判定规则**。它不产生新的设备读数——读数要等 `tools/collect_gpu_module_identity.sh` 在设备上跑完。先定口径，是为了避免"拿到数字之后各说各话"。

#### 3.6.1 现有三份采集为什么闭不了 U4-24

| U4-24 需要的字段 | 三份采集是否已有 | 缺了会怎样 |
| --- | :---: | --- |
| 模块名 | ✅ 有（`lsmod` 全表） | — |
| 是否装载 | ✅ 有 | — |
| 引用方向（谁用谁） | ✅ 有（`lsmod` used-by 列） | — |
| **模块文件的真实路径** | ❌ **无** | 不知道 `.ko` 在 `/vendor_dlkm`、`vendor_boot` ramdisk 还是内建 |
| **文件大小** | ❌ **无**（只有 `lsmod` 内存尺寸，口径不同，见 §3.6.2） | 无法与仓库比对 |
| **SHA256** | ❌ **无** | 无法排除"同尺寸异内容" |
| **vermagic** | ❌ **无** | **无法判定是否同一构建**（这是决定性判据） |
| `srcversion` | ❌ **无** | 无法比较源码上下文 |
| 版本串（`MODULE_VERSION`） | ⚠️ 部分（只有 3 个模块有 `/sys/module/*/version`） | 只能做弱对比 |

> 一句话：**`lsmod` 给的是"运行时视图"，U4-24 要的是"文件身份"**。二者不可互推。

#### 3.6.2 一处口径更正：`lsmod` 的 size **不是**文件大小

`/proc/modules` 第 2 字段是 `mod->core_layout.size`——模块在内存中的核心布局大小（**页对齐**），不是 `.ko` 的磁盘字节数。

| 证据 | 数值 |
| --- | --- |
| 设备 `lsmod` 中 GPU 相关（13 个链路模块 + 1 个消费方 `thermal_interface`）的 size | 2,494,464 / 40,960 / 12,288 / 684,032 / 28,672 / 24,576 / 12,288 / 53,248 / 73,728 / 65,536 / 90,112 / 32,768 / 32,768 / 69,632 |
| 是否全部为 4096 的整数倍 | **是（609 / 10 / 3 / 167 / 7 / 6 / 3 / 13 / 18 / 16 / 22 / 8 / 8 / 17 页）** |
| 仓库 15 个 `.ko` 文件大小是否为 4096 整数倍 | **否**（如 `ged.ko` 1,093,352 = 266.93 页；`mali_kbase…` 2,310,424 = 564.07 页） |

**影响**：

1. 本文件 §2.4、§3.2 与 `07` §3.2 中"`ged` 1,093,352 B vs 684,032 B，差 409 KB"的对比，是**内存尺寸 vs 文件尺寸**，**不能相减**。表述已改为"运行时内存 vs 仓库文件大小（仅方向参考）"。
2. D-007 的**主判据（vermagic 逐字符相等）不受影响**，结论不变；受影响的是**辅助判据**的证据力，由"足以排除"降为"方向一致"。
3. U4-24 的采集**必须**取 `FILE_SIZE_BYTES`，否则仍然无法与仓库比对。
4. **2026-11-16 实测结案**：设备 `ged.ko` 真实文件大小为 **1,093,352 B**，与仓库**完全相同**。之前那句"差 409 KB"不仅是口径错误，**结论方向也是错的**——两侧文件一样大。该表述已从全部文档删除，替换为 §3.2 的实测对比。

#### 3.6.4 vermagic 判定矩阵（输出回传后按此判）

`CONFIG_MODVERSIONS=y` 时内核按 **逐字符相等** 比较 `vermagic` 与 `VERMAGIC_STRING`，不符即拒绝装载，无 fallback。因此"装载成功"本身就是一条约束。

| 设备实测 `VERMAGIC_CHECK` | 判定 | 对 D-007 的影响 | 后续动作 |
| --- | --- | --- | --- |
| `YES`（串含 `6.6.143-android15-8-gf9aa2fec23c3-4k`） | 设备模块为本机内核构建 | 辅助判据升为实测 | U4-24a 闭合 |
| `NO`，串含 `6.6.118-…-g57e634f35c1b` | 设备上放的就是仓库那批 | D-007 被推翻 | 解释"为何 `modversions` 未拦住"（`--force`？`MODULE_FORCE_LOAD`？） |
| **`NO`，串是第三种——✅ 2026-11-16 实测命中：`6.6.118-…-g54a15cf3acba`** | 设备模块来自**另一个 6.6.118 构建**（原厂 OTA），不是本机运行内核 | D-007 成立，**理由须改写**（同 sublevel、不同 git 提交） | 必须解释"为何 `modversions` 未拦住"→ §3.7.4 |
| `NOT_FOUND` | `.modinfo` 被 strip / 读到压缩容器 | 不变 | `readelf -p .modinfo` 兜底；仍无则记 `[U]` |

**对第三分支预登记判读的更正（留痕）**：

本表在采集前把该分支的后果写成"**设备本身是混装** / 追加新风险 / **Stage 3 常量两面都不可用**"。实测后，这三句都要改：

| 预登记 | 实测后的正确表述 |
| --- | --- |
| "设备本身是混装" | **不准确**。设备是"厂商分区 + 第三方内核"，§2 早已定性，不是新发现。新发现是：**厂商模块的构建基线是 6.6.118**，与运行内核的 6.6.143 差一个 sublevel |

#### 3.6.5 哪些 Stage 3 / 03-REA 常量必须重导（本项的核心交付）

| 常量 | 依赖什么 | 为何与设备构建有关 | 是否必须重导 |
| --- | --- | --- | :---: |
| **`__versions` CRC** | **导出方**编译时按 genksyms 从符号类型算出的 crc | 设备 MTK 模块的 `__ksymtab` CRC 才是有效 oracle；仓库值来自 `6.6.118` 批次。r56p0 kbase 要导入 MTK 那 89 个符号，CRC 必须与**设备侧**一致 | **必须**（U4-24b） |
| **kCFI 类型哈希** | 函数**规范化后的类型** + clang 的类型哈希算法 | 值内嵌在**消费方模块**（`mtk_gpufreq_wrapper` 的 `*(int *)(fn-4)` 比较），与内核小版本**无直接关系**、与编译器/原型**强相关** | **必须重新取得 oracle**；预期与 `0x004b35c1` 等相同，但"预期"不算证据 |
| 结构体大小 / 字段偏移（`gpufreq_fp` 416 B / MGM 72 B） | 源码 + 配置宏 + ABI | 与构建配置相关；但这类量在"同标签、同架构、同 ABI"下高度稳定 | 建议核对，成本低（设备模块内偏移字面量即可印证） |
| 函数数 / 符号数 / 依赖方向（5,440 / 169 / 89） | 源码 | 与构建无关 | **不需要** |

**关键区分（最容易被写错的一条）**：

> `__versions` CRC 是**数值型 oracle**——必须从设备构建上取，取不到就没有替代品。
> kCFI 类型哈希是**类型型 oracle**——我们要做的其实是"让自建回调的原型与 MTK 期望完全一致"，哈希只是这个一致性的判据；设备值用于**验证**，不是用于"抄"。

**因此把 U4-24 拆成两个子项（不新增 UNKNOWN ID，计数不变）**：

| 子项 | 内容 | 能否用只读文本命令闭合 | 当前状态 |
| --- | --- | :---: | --- |
| **U4-24a** | 模块身份：路径 / 文件大小 / SHA256 / vermagic / srcversion | ✅ 能（`collect_gpu_module_identity.sh`） | **✅ 已闭合（2026-11-16 00:04，[D·A]）** |
| **U4-24b** | 数值：设备构建的 `__ksymtab` CRC、kCFI 期望常量 | ❌ 不能（设备无 `objdump`；需 `.readelf -x` 文本导出或 `.ko` 副本） | **开放**，范围已收窄至 kbase（§3.7.6） |

> **实测对 §3.6.5 的修正**：上表把"`__versions` CRC 必须重导"作为统一结论。实测后应改为**分层**——kbase 必须重导（`__versions` 514→513 条、srcversion 不同）；其余 14 个模块节大小逐字节相等，**沿用风险低**，严格起见只需一次 `readelf -x __versions` 文本比对即可定案。详见 §3.4 与 §3.7.6。

#### 3.7.4 关键发现：该内核绕过了 vermagic 强校验

| 事实 | 值 |
| --- | --- |
| 已装载的 15 个模块，其 `VERMAGIC_CHECK` | **全部 `NO`**（串为 `6.6.118-…-g54a15cf3acba-4k`） |
| 运行内核 `uname -r` | `6.6.143-android15-8-gf9aa2fec23c3-4k` |
| `CONFIG_MODVERSIONS` | 开启（vermagic 末尾含 `modversions`） |
| Linux 6.6 默认行为 | `same_magic()` **逐字符相等**，不符即 `-ENOEXEC`，无 fallback |

**结论**：串明确不符却全部装载成功 → **该内核必然打了 vermagic 检查绕过补丁**（KernelSU / SukiSU 系常见做法，用于允许加载非同版本模块）。

这条的后果比"模块不同源"严重得多：

| 影响 | 说明 |
| --- | --- |
| **"装载成功"不再是 ABI 证据** | 在任何打了此类补丁的内核上，"能 insmod / 能跑"**不能**证明 CRC 与原型兼容。这正是任务书禁止项 5 的实证，此前只是逻辑推断 |
| **Stage 5 验证环境须重新评估** | 若在原机上验证 r56p0 kbase，"通过"可能只是被补丁掩盖。**必须换到未打补丁的内核，或显式记录该前提** |
| **但仍有一条正向信息** | `check_version()`（符号 CRC 校验）是独立于 `same_magic()` 的另一道关卡。装载未报 `disagrees about version of symbol`，说明**要么 CRC 一致、要么该检查也被绕过**——两者无法从现有证据区分，归入 **U4-25**（第三方内核差异面） |

> **两条分支的判别方法**（下一步可选）：`dmesg | grep -i "version magic\|disagrees"`；或对第三方内核的 `kernel/module/version.c` 查补丁。前者只需 root，后者需内核源码（已有 `f9aa2fec` 提交，可查）。

#### 3.7.6 U4-24b 的最小闭合路径（成本已大幅下降）

由于 14 个模块的 `__versions` 节大小与仓库**逐个相等**，CRC 比对可以只做**一个样本**：

| 步骤 | 动作 | 产物 | 成本 |
| ---: | --- | --- | --- |
| 1 | 设备端 `readelf -x __versions /vendor_dlkm/lib/modules/ged.ko` | 纯十六进制文本（15,424 B → 约 96 KB 文本） | 一条命令 |
| 2 | 与仓库 `ged.ko` 同节逐条比对（按符号名对齐） | CRC 是否全等的判定 | 本地脚本 |
| 3 | 若**全等** → 两内核的导出符号 CRC 未变 → **14 个模块的 CRC 可沿用**，U4-24b 仅剩 kbase | 结论 | — |
| 4 | 若**不等** → 必须按设备构建重导；但设备无 `objdump`，需 `.ko` 副本（触及"不上传二进制"红线，须单独授权） | 结论 | 高 |

> **为什么只测 `ged` 就够**：`__versions` 记录的是"本模块期望的内核导出符号 CRC"，其值由**内核**决定，不由模块决定。同一内核下，不同模块看到的同名符号 CRC 必然一致。因此一个模块的全等即可外推到同一内核的其余模块。
>
> **kbase 例外**：它的 `__versions` 条数是 513（设备）vs 514（仓库），集合本身不同，不能靠"一个样本"外推——但这也正是它**必须重导**的独立理由。

## 4. 第三方补丁对 GPU 的间接影响

### 4.1 一条结构性事实：补丁改不到 GPU 驱动源码

| 事实 | 依据 |
| --- | --- |
| GKI `common/` 树**不含** Mali 驱动 | 仓库 `01_original_baseline/kernel_ref_mt6991/` 只有 `vendor_dlkm/*.ko`，无 `drivers/gpu/arm`；Mali 源码在 `vendor/mediatek/kernel_modules/gpu/…` |
| 构建补丁作用于 `common/` | 构建日志的 `.rej` 收集路径为 `common/mm/rmap.c` 一类 |
| 因此 | **任何 GKI 补丁都不可能修改 kbase / MGM / PMA / GED 的源码** |

**推论**：第三方补丁对 GPU 的影响**只能**是间接的（CPU 调度、频率、功耗、温控、可见性），**不可能**是"改了 GPU 驱动"。这条区分是任务书要求的，也正是最容易被写错的地方。

### 4.2 逐项影响评估

| 补丁 / 特性 | 类别 | 改 GPU 驱动源码？ | 可能的间接影响 | 等级 |
| --- | --- | :---: | --- | --- |
| **BORE scheduler** | CPU 调度器增强（burst 逻辑） | 否 | 改变渲染/合成线程的唤醒与抢占延迟 → 帧时间分布；**不影响 GPU 驱动内部** | **[P]**+**[E3]** |
| **CPUFreq governors（多 governor）** | CPU 调频策略 | 否 | CPU 频率分布变化 → 影响提交节奏与 MTK `gpufreq` 的负载判据 → 功耗与温升 → 可能更早触发热限幅 | **[P]**+**[E3]** |
| **CFS Fair Gaming Bias** | 调度偏置（前台/游戏加权） | 否 | 降低 jank 概率；同时改变 CPU 占用分布，间接影响 GPU 供帧 | **[P]**+**[E3]** |
| **MomenToMoiX QoS**（名称待核，疑为 `MomentX`） | QoS / uclamp 类 | 否 | 若涉及 uclamp/PMQoS，可能与 `mtk_gpufreq_wrapper`、`mtk_gpu_qos` 的限频请求路径交互 | **[P]**+**[U]** |
| **KernelSU** | 内核 hook + root | 否 | 不改 GPU；但改变 SELinux 域（`u:r:ksu:s0`），影响"服务访问 `/dev/mali0` 的权限路径"这一判断 | **[B]**+**[D·B]** |
| **SUSFS** | 文件视图隐藏 | 否 | **可隐藏路径** → 使"目录清单里没有"这一推断更弱（与 `07` §9 的限制叠加） | **[B]**+**[E2]** |
| **NoMount metamodule**（可选） | overlay 挂载 | 否 | 若安装，`/vendor` 视图可能被覆盖 → 影响 A 类归属（U4-27） | **[B]**+**[U]** |
| 网络 / BPF / TMPFS / DroidSpaces / BBG | 与图形无关 | 否 | 无 | **[B]** |

> `MomenToMoiX` 这一名称在公开清单中没有稳定对应（工作流里出现的是 `use_momentx` 开关）。本文件**不替它编造语义**，只按"QoS 类"给方向性判断，并标 [U]。

### 4.3 对 Stage 4 结论的污染面

| Stage 4 结论类型 | 是否被污染 | 理由 |
| --- | :---: | --- |
| UAPI 契约（ioctl / 结构体 / 标志 / 属性 ID） | **否** | 纯源码比对，与运行内核无关 |
| 固件加载逻辑与版本校验 | **否** | 纯源码 |
| 设备文件存在性 / 大小 / 哈希（A 类） | **基本否** | `vendor` 未被本次安装改动；但 overlay 可见性未排除（U4-27） |
| 运行内核版本与模块装载（B/C 类） | **是** | 观测对象是第三方内核；结论须限定"在第三方内核上" |
| 性能 / 功耗 / 温控观测 | **是（且不可用）** | 调度与调频补丁直接改变这些量，不能代表原厂表现 |
| bootloop 判定（U4-10） | **否** | 本来就没有故障证据，仍为 UNKNOWN |

### 4.4 三条禁止推断

1. **不得**由"第三方内核能装载原厂 `.ko`"推出"r56p0 kbase 也能装载"——前者只证明 GKI KMI 未变，后者取决于 MTK 模块导出符号的 CRC。
2. **不得**由"换了内核 GPU 仍正常"推出"换 kbase 也安全"——kbase 是 GPU 栈的**根**，不是叶子。
3. **不得**把第三方补丁造成的帧率/功耗变化，记入"GPU 驱动性能"评价。

## 7. 最终证据可信度评估

### 7.1 分层评分

| 证据面 | 可信度 | 理由 | 适用边界 |
| --- | :---: | --- | --- |
| A 类文件元数据（路径/大小/哈希） | **高** | 采集直接可读；`vendor` 未被本次安装改动 | 不覆盖 OTA 前状态与 overlay |
| B 类运行时状态 | **中高** | 第三方内核已由 `u:r:ksu:s0` 证实；但"哪一次构建"未定 | 仅代表该内核 + 该 ROM 的组合 |
| C 类模块装载事实 | **高** | `lsmod` + `/dev/mali0` + 服务 pid 三方一致 | 仅"装载成功"，不含符号粒度；**且该内核绕过 vermagic，装载成功本身不构成 ABI 证据** |
| C 类模块二进制来源 | **高（本轮升级）** | 18 个文件路径/大小/SHA256/vermagic 全部实测；14/15 与仓库结构一致、kbase 实质差异、3 个仓库缺件（§3.7.1） | 不可用于二进制级定量结论（CRC 值仍未比对） |
| 仓库源码结论（UAPI/加载器） | **高** | 与设备环境无关 | 不受本轮影响 |
| 仓库 `.ko` 二进制结论（CRC/kCFI） | **中 → 分层** | 14 个模块节大小与设备逐个相等，kbase 不同 | kbase 必须重导；其余可沿用（§3.4、§3.7.6） |
| 性能 / 功耗 / 温控 | **低** | 调度与调频补丁直接污染 | 不可用于对比原厂 |

### 7.2 可以拿去用的三条

1. **UAPI 契约兼容**（28/28 ioctl、30/30 结构体、83/83 属性 ID、能力表保留 ≤1.30 语义）——纯源码，与本轮来源问题无关。
2. **A 类专业结论**：原厂固件/DDK/Vulkan 薄壳/mapper/HWC 的**存在性、体积、依赖关系**。
3. **模块身份对照结论**：18 个设备 `.ko` 的路径/大小/SHA256/vermagic/srcversion 已实测，与仓库基线逐项对照完成（§3.7.1）——**这是本轮最硬的产出**。

### 7.3 不能拿去用的三条

1. "原厂内核环境下实测"——不存在这样的观测。
2. "设备 `.ko` = 仓库 `.ko`"——vermagic 与 SHA256 均不同；**但也不能反过来说"差异很大"**，14/15 个模块结构一致。
3. "组合 A 已在原厂环境验证"——组合 A 只被证明"在第三方内核上可用"，且该内核**绕过了 vermagic 校验**，连"ABI 兼容"都不能由装载成功推出。

1. **证据归属已澄清**：A 类（厂商文件）/ B 类（第三方内核运行时）/ C 类（厂商模块）三者的来源不同，此前一律记作"真机实测"是口径错误。
2. **安装范围已核验**：仅 `boot`；不碰 `vendor` / `vendor_dlkm`；不含 `.ko` / 固件 / `.so`。
3. **模块来源已精确分层**：设备 `.ko` 与仓库 `.ko` **不是同一构建**——vermagic 分别为 `6.6.118-…-g54a15cf3acba`（原厂 OTA）与 `6.6.118-…-g57e634f35c1b`（OS3.0.305.0），**同 sublevel、不同提交**。14/15 个模块的 `.text` 与 `__versions` 节大小逐字节相等，`mali_mgm`/`mali_prot_alloc` 的 `srcversion` 逐字符相同；**只有 kbase 有实质差异**（+17,640 B、`.text` +6,788 B、`__versions` +1 条）。**模块集合也不对称**：设备 18 个文件，仓库 15 个，缺 `mtk_ghpm`、`mtk_cg_peak_power_throttling`、`mtk_smmu_qos`（§3.7.1、§3.7.5）。
4. **补丁影响已定性**：只能间接（调度/频率/温控/可见性），**不可能**改 GPU 驱动源码；性能类观测不可用于对比原厂。
5. **发现一处环境级风险**：运行内核**绕过 vermagic 强校验**（15 个模块串不符仍全部装载），因此"装载成功 / 能跑"在本机**不能**作为 ABI 兼容证据（§3.7.4）。
6. **两层版本事实被改写**：`6.6.143` 是第三方运行内核，**不是原厂内核**；厂商模块的构建基线是 `6.6.118-android15-8-g54a15cf3acba`，原厂 boot 的内核据此推定为同一串（[E2]）（§3.1、§3.7.2）。
7. **两项 P0 + 一项 P1 仍未闭合**：U4-04（行为面）、U4-12（固件实体）、U4-24b（CRC/kCFI 数值，范围已收窄至 kbase）；Stage 5 可设计、不可定论、不可实施。
8. **口径更正两处**：`lsmod` 的 size 是内存尺寸而非文件大小，历史表述"`ged` 差 409 KB"**连方向都错**（实测两侧文件完全相同）；另一处是"第三种 vermagic 串"的预登记判读过度悲观，已更正（§3.2、§3.6.4）。
