# DECISION_LOG — 项目决策日志

> 本文件记录**已经形成**的决策，供后续 Agent 判断"哪些事已有定论、哪些还能改"。
>
> 每条决策包含：ID、决策内容、背景、证据来源、证据等级、当前状态、是否允许重新审议。
>
> **原则**：推断不得伪装成决策。凡证据不足者，状态标 `待执行` 或 `条件性生效`，并在"再审议"列写明触发条件。

| 字段 | 取值约定 |
| --- | --- |
| 状态 | `生效`（已定，按此执行） / `生效（条件性）`（有前提，前提变化需复审） / `待执行`（已决定但尚未落地） / `已被取代`（保留历史） |
| 再审议 | `否`（属项目定义，不可改） / `需用户授权` / `新证据即可`（Agent 可依新证据提出修订） |

### D-018 · 模块身份以「文件身份」判定，不以「运行时视图」判定；`lsmod` 的 size ≠ 文件大小

| 项 | 内容 |
| --- | --- |
| **决策** | 判定"设备 `.ko` 与仓库 `.ko` 是否同一构建"，**必须**取文件级证据（路径 / 文件大小 / SHA256 / `vermagic` / `srcversion`）。`lsmod` 只提供运行时视图，其中第 2 字段是 `mod->core_layout.size`（内存、页对齐），**不得**与仓库 `.ko` 的磁盘字节数相减或直接比对。 |
| **背景** | 此前 `08` §2.4/§3.2、`07` §3.2/§3.4 写"`ged` 1,093,352 B vs 684,032 B，差 409 KB，已足以排除同一二进制"——前者是文件大小，后者是内存尺寸，**量纲不同**。实测佐证：设备 14 个模块的 `lsmod` size 全部是 4096 的整数倍（609/10/3/167/7/6/3/13/18/16/22/8/8/17 页），而仓库 15 个 `.ko` 的文件大小均非 4096 倍数。 |
| **证据来源** | `05/08` §3.6.2；`/proc/modules` 语义（`core_layout.size`）；设备三份采集的 `lsmod` 段；`01_original_baseline/kernel_ref_mt6991/vendor_dlkm/` 文件字节数 |
| **证据等级** | **[D·B]**（设备运行时）+ **[E1]**（内核数据结构的输出字段）+ **[E1]**（文件大小实测） |
| **状态** | 生效 |
| **再审议** | **否**（属量纲约定）。但若日后取得设备 `.ko` 副本，可用"文件大小 vs `lsmod` size 的页对齐关系"反向校验该约定 |

### D-019 · kCFI 哈希属「类型型 oracle」，`__versions` CRC 属「数值型 oracle」，二者重导策略不同

| 项 | 内容 |
| --- | --- |
| **决策** | U4-24 拆为两个子项：**a = 身份**（路径/大小/SHA256/vermagic/srcversion，可只读闭合）、**b = 数值**（设备 `__ksymtab` CRC、kCFI 期望常量，需反汇编或 `.ko` 副本）。重导策略分开表述：<br>① **`__versions` CRC 是数值型 oracle**——必须从**设备构建**取得，取不到就没有替代品；<br>② **kCFI 类型哈希是类型型 oracle**——本质要求是"自建回调的**函数原型**与 MTK 期望完全一致"，设备值用于**验证**该一致性，**不是**用于照抄；<br>③ 结构体大小/字段偏移建议核对（低成本）；④ 函数数/符号数/依赖方向**不受影响**。 |
| **背景** | `04_mtk_platform/REA_SUPPLEMENT.md` 的 R-1 只说了"必须保持原型一致"，未区分两类常量的可替代性；笼统写作"CRC/kCFI 都要重导"会让后续 Agent 误以为两者都是"抄常量"。实际上 kCFI 哈希与内核小版本无关（取决于类型 + clang 哈希算法），而 CRC 与导出方构建强相关。 |
| **证据来源** | `05/08` §3.6.5；`04_mtk_platform/REA_SUPPLEMENT.md` §10 R-1、§3.4；`docs/PROJECT_STATE.md` §5.4 |
| **证据等级** | **[E1]**（REA 反编译观察到的 `*(int*)(fn-4)` 比较）+ **[E2]**（由 genksyms 与 kCFI 的生成机制推导） |
| **状态** | 生效（**子项 a 已闭合**，2026-11-16；子项 b 未开始；本决策规定的是"如何做"，不是"已完成"） |
| **再审议** | 新证据即可（若设备实测的 kCFI 常量与 `0x004b35c1` 等**不同**，则须重新评估"与内核版本无关"这一前提，并检查 clang 版本差异） |

| **决策** | 全仓库统一三层表述，禁止用单一"设备内核 6.6.143"：<br>① **运行内核**（第三方）`6.6.143-android15-8-gf9aa2fec23c3-4k`；<br>② **原厂内核（推定）** `6.6.118-android15-8-g54a15cf3acba-4k`；<br>③ **仓库基线内核** `6.6.118-android15-8-g57e634f35c1b-4k`（OS3.0.305.0）。 |

### D-021 · 运行内核绕过了 vermagic 校验，因此「装载成功」不构成 ABI 证据

| 项 | 内容 |
| --- | --- |
| **决策** | 在**当前运行内核**上，"模块能 insmod / 能跑"**不得**作为 ABI 兼容证据。任何基于该环境的验证结论，必须显式标注此前提；Stage 5 若要在实机验证，须换到未打该类补丁的内核，或记录"结果可能被补丁掩盖"。 |
| **背景** | 15 个已装载模块的 `VERMAGIC_MATCHES_UNAME_R` **全部为 `NO`**（模块串 `6.6.118-…-g54a15cf3acba`，内核 `6.6.143-…-gf9aa2fec23c3`）。Linux 6.6 的 `same_magic()` 是逐字符比较、不符即 `-ENOEXEC`、无 fallback。串明确不符却全部装载成功 → 内核必然存在绕过补丁（KernelSU/SukiSU 系常见）。 |
| **背景补充** | `check_version()`（符号 CRC 校验）是另一道独立关卡。装载未报 `disagrees about version of symbol`，说明**要么 CRC 一致、要么该检查也被绕过**，两者无法从现有证据区分 → 归入 U4-25。 |
| **证据来源** | `05/08` §3.7.4；`05/07` §3.5（18 个模块的 vermagic 与装载状态） |
| **证据等级** | **[D·A]**（vermagic 与装载状态均为实测）+ **[E2]**（`same_magic` 行为来自内核源码常识） |
| **状态** | 生效 |
| **再审议** | 若在设备上 `dmesg` 未发现绕过痕迹，或对第三方内核源码（`f9aa2fec`）核查后确认未改 `kernel/module/`，则本条被推翻——但"串不符仍装载"这一实测事实本身无法被解释，故推翻概率极低 |

### D-022 · REA 常量重导范围由 15 个模块收窄至 kbase

| 项 | 内容 |
| --- | --- |
| **决策** | `04_mtk_platform/REA_SUPPLEMENT.md` 的 kCFI 与 `__versions` CRC **只对 kbase 必须重导**；其余 14 个模块的 `.text` 与 `__versions` 节大小与仓库基线逐字节相等，可先用"单样本 `readelf -x __versions`"验证后沿用。 |
| **背景** | 实测对照：15 个可比对模块中 **14 个文件字节数与关键节大小完全相同**；`mali_mgm`/`mali_prot_alloc` 的 `srcversion` 与仓库**逐字符相同**（源码未变）。唯一实质差异是 kbase：文件 +17,640 B、`.text` +6,788 B、`__versions` 514→513 条、`srcversion` 不同。 |
| **背景补充** | 该收窄**不改变** D-013（"Stage 3 常量需重导"）的方向，只改变**工作量估计**。且"节大小相同"≠"CRC 值相同"——后者由内核构建决定，故仍需一次抽样验证。 |
| **证据来源** | `05/08` §3.4、§3.7.1、§3.7.3、§3.7.6；本地对 `01_original_baseline/…/vendor_dlkm/*.ko` 的 `readelf -SW` 实测 |
| **证据等级** | **[D·A]**（设备侧）+ **[E1]**（仓库侧） |
| **状态** | 生效 |
| **再审议** | 若单样本比对发现 CRC 不等，则本条被推翻，须退回"逐模块重导" |
