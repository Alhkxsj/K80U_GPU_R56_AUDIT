# 08 — 第三方 GKI 环境下的设备证据来源审计

> **本文件回答什么**：Stage 4 的全部"真机实测"结论，究竟来自**原厂环境**还是**第三方内核环境**？厂商文件、运行时状态、内核模块这三类证据能否分开？分开之后，哪些结论仍然成立、哪些必须降级？
>
> **一句话结论**：设备当前运行的是**第三方 GKI 内核**（KernelSU 补丁，内核源码提交 `f9aa2fec`），而 `/vendor` 下的 GPU 文件与 `/vendor_dlkm` 下的 GPU 模块属于**厂商分区内容**，未被该安装包改动。因此 **Stage 4 的实测证据是"厂商分区 + 第三方内核"的混合环境**，此前一律记作"真机实测 / 出厂状态"是**口径错误**；本次按 A/B/C 三类拆分并重标。
>
> **本文件不做**：不重跑 Stage 1–4，不刷机，不替换驱动，不做移植设计，不进入 Stage 5。

## 0. 摘要

### 0.1 证据等级扩展（本轮新增两级）

| 级别 | 含义 | 可反驳性 |
| --- | --- | --- |

### 1.3 安装脚本的实际参数

AnyKernel3 模板来自 `WildKernels/AnyKernel3` 分支 `gki-2.0`，其 `anykernel.sh` 的原文参数：

```sh
do.devicecheck=0
do.modules=0
do.systemless=0
do.cleanup=1
do.cleanuponabort=0
do.check_boot_version=0
...
block=boot
is_slot_device=auto
ramdisk_compression=auto
patch_vbmeta_flag=auto
```

安装流程（同一文件）：

```sh
split_boot
if [ -f "$SPLITIMG/ramdisk.cpio" ]; then
  unpack_ramdisk
  write_boot      # 仅重写 boot 分区
else
  flash_boot
fi
```

| 参数 | 取值 | 对来源归属的意义 |
| --- | --- | --- |
| `block=boot` | **boot** | 只处理 `boot` 分区；`init_boot` / `vendor_boot` / `dtbo` 不参与 |
| `do.modules=0` | 关 | **不安装任何 `.ko`**，即使包内有也不会写入 |
| `do.systemless=0` | 关 | 不做 systemless 覆盖（不往 `/system`、`/vendor` 注入） |
| `patch_vbmeta_flag=auto` | 自动 | 可能改写 **vbmeta 验证标志**（属 boot 侧验证链），**不改分区内容** |
| `do.check_boot_version=0` | 关 | 不校验 boot 版本，允许跨 ROM 刷入 |

### 1.4 安装范围结论

| 动作 | 是否发生 | 依据 |
| --- | :---: | --- |
| 写 `boot` 分区 | **是** | `block=boot` + `write_boot` |
| 写 `init_boot` / `vendor_boot` / `dtbo` | 否 | 脚本无对应路径 |
| 写 `vendor` | **否** | 脚本无 `vendor` 路径；`do.systemless=0` |
| 写 `vendor_dlkm` | **否** | 同上；且 `do.modules=0` |
| 安装内核模块 `.ko` | **否** | `do.modules=0`；产物无 modules |
| 安装 CSF 固件 | **否** | 产物无 `.bin` |
| 安装 GPU 用户态库 | **否** | 产物无 `.so`；APK 单独安装 |
| 改 AVB 验证标志 | 可能 | `patch_vbmeta_flag=auto` |

佐证（`[D·A]`）：设备属性 `ro.vendor.build.ab_ota_partitions` 明确列出 `boot`、`init_boot`、`vendor_boot`、`vendor`、`vendor_dlkm`、`dtbo` 为**彼此独立的分区**。仅写 `boot` 不会波及其余分区。

### 1.5 这个结论不能推出什么

| 不能推出 | 原因 |
| --- | --- |
| "设备全部文件与出厂一致" | 只证明**本次安装**未改 vendor；不覆盖 OTA 升级、其他模块（Magisk / KSU 元模块）、用户手工改动 |
| "`/vendor` 内容未被任何机制覆盖" | `NoMount-Metamodule` 是**可选**安装项，具备 overlay 挂载能力；采集未记录 mount 表（U4-27） |
| "内核是原厂内核" | 恰恰相反：`u:r:ksu:s0` 证明内核已被 KernelSU 补丁化 |
| "第三方内核改动面仅限 KernelSU" | 同一构建还启用了调度/调频等补丁（§4） |

## 2. 三类设备证据分类

### 2.1 分类规则

| 类别 | 定义 | 标签 | 判据来源 |
| --- | --- | --- | --- |
| **A. 厂商分区静态文件** | `/vendor`、`/system` 等**只读分区**上的文件，由厂商 ROM 提供，本次安装未改动 | `[D·A]` | 路径 + 大小 + SHA256 + ELF 头 |
| **B. 第三方 GKI 运行时状态** | 由**当前运行内核**产生的状态：`uname`、`lsmod`、`/sys/module`、`/dev/mali0`、服务 pid、getprop、DT | `[D·B]` | 运行时命令输出 |
| **C. 厂商内核模块** | `/vendor_dlkm` 提供的 `.ko`，**文件属厂商、装载于第三方内核** | `[D·C]` | `lsmod` + `/sys/module/*/version` + 文件元数据 |

> **B 与 C 的关系是本文件的核心**：C 是**文件**（厂商来源），B 是**状态**（第三方来源）。同一个 `modprobe` 事件同时产生 C 的"存在"与 B 的"已装载"，但**来源归属相反**。把它写成"原厂内核已装载原厂模块"就把两件事合并了。

## 3. GPU 模块来源核验

### 3.1 决定性判据：vermagic 不可能同时成立

| 证据 | 值 |
| --- | --- |
| 仓库 15 个 `.ko` 的 vermagic（抽样 3 个实测一致） | `6.6.118-android15-8-g57e634f35c1b-4k SMP preempt mod_unload modversions aarch64` |
| 设备运行内核 | `6.6.143-android15-8-gf9aa2fec23c3-4k` |

```
modversions 开启时：
  .ko 的 vermagic 必须与内核 version 串逐字符相等
  6.6.118-android15-8-g57e634f35c1b-4k  ≠  6.6.143-android15-8-gf9aa2fec23c3-4k
  → 仓库基线 .ko 无法装载到当前设备内核
  → 设备上装载的 .ko 必然是另一次构建
```

**结论**：设备侧 GPU `.ko` 与仓库基线 `.ko` **不是同一份二进制**，只能同属一个**源码标签**（`r49p1-03bet0`）。

### 3.2 辅助判据：运行时内存尺寸与时间戳

| 判据 | 仓库 | 设备 | 说明 |
| --- | --- | --- | --- |
| vermagic（**决定性**） | `6.6.118-android15-8-g57e634f35c1b-4k SMP preempt mod_unload modversions aarch64` | 运行内核 `6.6.143-android15-8-gf9aa2fec23c3-4k` | **不相等 → 仓库 `.ko` 无法装载到当前内核**；反过来说，**当前内核上装载成功的 `.ko` 必然带 143 的 vermagic** |
| `ged` 运行时内存 vs 仓库文件大小 | 文件 1,093,352 B | `lsmod` 报 684,032 B | **口径不同**（`lsmod` 第 2 字段是 `core_layout.size`，页对齐；不是文件大小，见 §3.6.2）。**方向可参考，数值不可相减** |
| 构建时间 | — | `Mon Oct 5 04:20:00 UTC 2026` | **不可作判据**：GKI 可复现构建常固定 `KBUILD_BUILD_TIMESTAMP`；且原厂 boot 与第三方 boot 都基于同一 GKI 提交，串相同 |

> 时间戳这条要特别说明：run #11 发生在 11-14，而 `uname -v` 显示 10-05。**这不能推出"设备没刷这个包"**，也不能推出"刷了"——因为两条路径都可能产生 10-05（固定时间戳 / 刷的是更早一次同配置构建）。所以"是否为 run #11 的字节"记为 **U4-26**，而不是结论。

### 3.3 四档结论（按任务书要求分层）

| 档位 | 内容 | 证据 |
| --- | --- | --- |
| **① 已证实与仓库原厂源码版本对应** | 运行中 kbase 的版本串 `r49p1-03bet0` 与仓库基线 `MALI_RELEASE_NAME` 逐字符一致；UK ABI 1.30 与 r49p1 UAPI 头常量一致 | **[D·C]**+**[E1]** |
| **② 第三方 GKI 环境下实际装载** | 12 个模块已装载；`/dev/mali0` 存在；图形服务在跑 | **[D·B]**+**[D·C]** |
| **③ 来源高度吻合但未经镜像比对** | 仓库 15 个 `.ko` 取自社区设备树镜像 `xiaomi-mt6991-devs/android_device_xiaomi_dali-kernel@0576426`，**未与官方 OTA 镜像逐字节比对**；设备侧 `.ko` 的 SHA256 / vermagic **未采集** | **[E1]**+**[U]** |
| **④ UNKNOWN** | 设备 `.ko` 的具体哈希、构建号、是否与官方镜像一致；第三方内核导出的符号集是否与原厂 boot 完全一致 | **[U]** |

> **不能做的事**：把②当作①。装载成功只说明"KMI 兼容"，不说明"文件同源"，更不说明"原厂内核也如此"。

### 3.4 对 TASK 03 数值结论的影响

Stage 3 / 03-REA 的**二进制级数字**是在 `6.6.118` 那批 `.ko` 上测的。逐类评估：

| 结论类型 | 示例 | 是否受构建代次影响 | 处理 |
| --- | --- | :---: | --- |
| 源码级结构（函数指针表项数、成员顺序） | `gpufreq_fp` 416 B / 52 项、MGM ops 72 B | 低（取决于配置宏，标签相同则大概率不变） | 保留，标注"基于 6.6.118 构建" |
| 符号计数与依赖方向 | kbase→MTK 89 处、GED 导出 168、无外部引用 114 | 低（源码级） | 保留 |
| **kCFI 类型哈希** | `slot[15]=0x004b35c1` 等 | **高**（编译器/配置相关） | **必须在设备构建上重导** |
| **`__versions` CRC** | 各导出符号的 crc | **高**（随内核符号类型/版本） | **必须重导**（U4-24） |
| 模块大小 / 段布局 | `ged` 1,093,352 B | 高 | 已按 §3.2 更正为"仓库基线值" |

### 3.5 一个正向副产物：KMI 兼容性已被实机证明

厂商 GPU 模块能在**重新编译的** `6.6.143` GKI 内核上装载并正常工作，说明：

1. 该第三方内核保留了 GKI KMI（`android15-8` 世代）的导出符号与 CRC；
2. "换内核"这条路在**模块装载层面**是通的——这与 Stage 5 关心的"能否在自建内核上跑厂商 GPU 栈"直接相关。

> 但这**不构成** r56p0 的兼容性证据：r56p0 kbase 需要的是**MTK 模块导出的那 89 个符号及其 CRC** 与自身引用匹配（TASK 03 已证反向依赖为 0），这与"GKI 导出集未变"是两件事。

### 3.6 U4-24：模块身份核验的口径、判定矩阵与"哪些常量必须重导"

> 本节是 U4-24 的**方法学与判定规则**。它不产生新的设备读数——读数要等 `tools/collect_gpu_module_identity.sh` 在设备上跑完。先定口径，是为了避免"拿到数字之后各说各话"。

#### 3.6.1 现有三份采集为什么闭不了 U4-24

| U4-24 需要的字段 | 三份采集是否已有 | 缺了会怎样 |
| --- | :---: | --- |
| 模块名 | ✅ 有（`lsmod` 全表） | — |
| 是否装载 | ✅ 有 | — |
| 引用方向（谁用谁） | ✅ 有（`lsmod` used-by 列） | — |
| **模块文件的真实路径** | ❌ **无** | 不知道 `.ko` 在 `/vendor_dlkm`、`vendor_boot` ramdisk 还是内建 |
| **文件大小** | ❌ **无**（只有 `lsmod` 内存尺寸，口径不同，见 §3.6.2） | 无法与仓库比对 |
| **SHA256** | ❌ **无** | 无法排除"同尺寸异内容" |
| **vermagic** | ❌ **无** | **无法判定是否同一构建**（这是决定性判据） |
| `srcversion` | ❌ **无** | 无法比较源码上下文 |
| 版本串（`MODULE_VERSION`） | ⚠️ 部分（只有 3 个模块有 `/sys/module/*/version`） | 只能做弱对比 |

> 一句话：**`lsmod` 给的是"运行时视图"，U4-24 要的是"文件身份"**。二者不可互推。

#### 3.6.2 一处口径更正：`lsmod` 的 size **不是**文件大小

`/proc/modules` 第 2 字段是 `mod->core_layout.size`——模块在内存中的核心布局大小（**页对齐**），不是 `.ko` 的磁盘字节数。

| 证据 | 数值 |
| --- | --- |
| 设备 `lsmod` 中 GPU 相关（13 个链路模块 + 1 个消费方 `thermal_interface`）的 size | 2,494,464 / 40,960 / 12,288 / 684,032 / 28,672 / 24,576 / 12,288 / 53,248 / 73,728 / 65,536 / 90,112 / 32,768 / 32,768 / 69,632 |
| 是否全部为 4096 的整数倍 | **是（609 / 10 / 3 / 167 / 7 / 6 / 3 / 13 / 18 / 16 / 22 / 8 / 8 / 17 页）** |
| 仓库 15 个 `.ko` 文件大小是否为 4096 整数倍 | **否**（如 `ged.ko` 1,093,352 = 266.93 页；`mali_kbase…` 2,310,424 = 564.07 页） |

**影响**：

1. 本文件 §2.4、§3.2 与 `07` §3.2 中"`ged` 1,093,352 B vs 684,032 B，差 409 KB"的对比，是**内存尺寸 vs 文件尺寸**，**不能相减**。表述已改为"运行时内存 vs 仓库文件大小（仅方向参考）"。
2. D-007 的**主判据（vermagic 逐字符相等）不受影响**，结论不变；受影响的是**辅助判据**的证据力，由"足以排除"降为"方向一致"。
3. U4-24 的采集**必须**取 `FILE_SIZE_BYTES`，否则仍然无法与仓库比对。

#### 3.6.3 任务书给的模块名 vs 设备实际模块名

任务书列了 8 个名字，并明确要求"不要假定都以独立 `.ko` 存在"。实测结果支持这个提醒：**其中 4 个不是模块名，而是 kbase 内部组件名**。

| 任务书名字 | 设备实际 | 性质 |
| --- | --- | --- |
| `mali_kbase_mt6991` | `mali_kbase_mt6991_r49` | 名字少了 `_r49` 后缀 |
| `ged` | `ged` | 一致 |
| `gpufreq` | `mtk_gpufreq_mt6991` **+** `mtk_gpufreq_wrapper` | **一个名字对应两个模块** |
| `gpueb` | `mtk_gpueb` | 前缀不同 |
| `mali_kbase_mem_pool_group_manager` | — | **kbase 内部组件，无独立 `.ko`** |
| `mali_kbase_mem_pool_manager` | — | 同上 |
| `mali_kbase_mgm` | `mali_mgm_mt6991_r49` | 组件名 → 独立模块（MGM 内存组管理） |
| `mali_kbase_pma` | `mali_prot_alloc_mt6991_r49` | 组件名 → 独立模块（受保护内存分配） |

**不纳入本项的三类**（各有明确排除理由）：

| 模块 | 排除理由 |
| --- | --- |
| `thermal_interface`、`mtk_fpsgo`、`mtk_mbraink_v6991`、`mtk_cg_peak_power_throttling`、`mediatek_drm` 等 | 它们的 used-by 列表里含 GPU 模块 → 是 GPU 模块的**消费方**（上游），不是 GPU 驱动链本身。按"谁被 GPU 模块依赖"判定，不按"名字里有没有 gpu"判定 |

#### 3.6.4 vermagic 判定矩阵（输出回传后按此判）

`CONFIG_MODVERSIONS=y` 时内核按 **逐字符相等** 比较 `vermagic` 与 `VERMAGIC_STRING`，不符即拒绝装载，无 fallback。因此"装载成功"本身就是一条约束。

| 设备实测 `VERMAGIC_CHECK` | 判定 | 对 D-007 的影响 | 后续动作 |
| --- | --- | --- | --- |
| `YES`（串含 `6.6.143-android15-8-gf9aa2fec23c3-4k`） | 设备模块为本机内核构建 | **辅助判据升为实测**，D-007 由 `[E1]+[E2]` 升 `[E1]+[D·C]` | U4-24a 闭合；U4-24b（数值）另议 |
| `NO`，串含 `6.6.118-…-g57e634f35c1b` | 设备上放的就是仓库那批 | **D-007 被推翻** → 必须重写本文件 §3、`07` §3.4、D-013 | 解释"为何 `modversions` 未拦住"（`--force`？`MODULE_FORCE_LOAD`？） |
| `NO`，串是第三种（如 `6.6.143-…-g<另一哈希>`） | 内核与模块来自**不同提交** | 比 D-007 更强的结论：**设备本身是混装** | 追加一条新风险；Stage 3 常量两面都不可用 |
| `NOT_FOUND` | `.modinfo` 被 strip / 读到压缩容器 | 不变 | 用 `readelf -p .modinfo` 兜底；仍无则记 `[U]` |

#### 3.6.5 哪些 Stage 3 / 03-REA 常量必须重导（本项的核心交付）

| 常量 | 依赖什么 | 为何与设备构建有关 | 是否必须重导 |
| --- | --- | --- | :---: |
| **`__versions` CRC** | **导出方**编译时按 genksyms 从符号类型算出的 crc | 设备 MTK 模块的 `__ksymtab` CRC 才是有效 oracle；仓库值来自 `6.6.118` 批次。r56p0 kbase 要导入 MTK 那 89 个符号，CRC 必须与**设备侧**一致 | **必须**（U4-24b） |
| **kCFI 类型哈希** | 函数**规范化后的类型** + clang 的类型哈希算法 | 值内嵌在**消费方模块**（`mtk_gpufreq_wrapper` 的 `*(int *)(fn-4)` 比较），与内核小版本**无直接关系**、与编译器/原型**强相关** | **必须重新取得 oracle**；预期与 `0x004b35c1` 等相同，但"预期"不算证据 |
| 结构体大小 / 字段偏移（`gpufreq_fp` 416 B / MGM 72 B） | 源码 + 配置宏 + ABI | 与构建配置相关；但这类量在"同标签、同架构、同 ABI"下高度稳定 | 建议核对，成本低（设备模块内偏移字面量即可印证） |
| 函数数 / 符号数 / 依赖方向（5,440 / 169 / 89） | 源码 | 与构建无关 | **不需要** |

**关键区分（最容易被写错的一条）**：

> `__versions` CRC 是**数值型 oracle**——必须从设备构建上取，取不到就没有替代品。
> kCFI 类型哈希是**类型型 oracle**——我们要做的其实是"让自建回调的原型与 MTK 期望完全一致"，哈希只是这个一致性的判据；设备值用于**验证**，不是用于"抄"。

**因此把 U4-24 拆成两个子项（不新增 UNKNOWN ID，计数不变）**：

| 子项 | 内容 | 能否用只读文本命令闭合 |
| --- | --- | :---: |
| **U4-24a** | 模块身份：路径 / 文件大小 / SHA256 / vermagic / srcversion | ✅ 能（`collect_gpu_module_identity.sh`） |
| **U4-24b** | 数值：设备构建的 `__ksymtab` CRC、kCFI 期望常量 | ❌ 不能。需要在设备侧反汇编（无 `objdump`），或取得 `.ko` 副本后离线做——后者触及"不上传二进制"红线，须用户单独授权 |

## 4. 第三方补丁对 GPU 的间接影响

### 4.1 一条结构性事实：补丁改不到 GPU 驱动源码

| 事实 | 依据 |
| --- | --- |
| GKI `common/` 树**不含** Mali 驱动 | 仓库 `01_original_baseline/kernel_ref_mt6991/` 只有 `vendor_dlkm/*.ko`，无 `drivers/gpu/arm`；Mali 源码在 `vendor/mediatek/kernel_modules/gpu/…` |
| 构建补丁作用于 `common/` | 构建日志的 `.rej` 收集路径为 `common/mm/rmap.c` 一类 |
| 因此 | **任何 GKI 补丁都不可能修改 kbase / MGM / PMA / GED 的源码** |

**推论**：第三方补丁对 GPU 的影响**只能**是间接的（CPU 调度、频率、功耗、温控、可见性），**不可能**是"改了 GPU 驱动"。这条区分是任务书要求的，也正是最容易被写错的地方。

### 4.2 逐项影响评估

| 补丁 / 特性 | 类别 | 改 GPU 驱动源码？ | 可能的间接影响 | 等级 |
| --- | --- | :---: | --- | --- |
| **BORE scheduler** | CPU 调度器增强（burst 逻辑） | 否 | 改变渲染/合成线程的唤醒与抢占延迟 → 帧时间分布；**不影响 GPU 驱动内部** | **[P]**+**[E3]** |
| **CPUFreq governors（多 governor）** | CPU 调频策略 | 否 | CPU 频率分布变化 → 影响提交节奏与 MTK `gpufreq` 的负载判据 → 功耗与温升 → 可能更早触发热限幅 | **[P]**+**[E3]** |
| **CFS Fair Gaming Bias** | 调度偏置（前台/游戏加权） | 否 | 降低 jank 概率；同时改变 CPU 占用分布，间接影响 GPU 供帧 | **[P]**+**[E3]** |
| **MomenToMoiX QoS**（名称待核，疑为 `MomentX`） | QoS / uclamp 类 | 否 | 若涉及 uclamp/PMQoS，可能与 `mtk_gpufreq_wrapper`、`mtk_gpu_qos` 的限频请求路径交互 | **[P]**+**[U]** |
| **KernelSU** | 内核 hook + root | 否 | 不改 GPU；但改变 SELinux 域（`u:r:ksu:s0`），影响"服务访问 `/dev/mali0` 的权限路径"这一判断 | **[B]**+**[D·B]** |
| **SUSFS** | 文件视图隐藏 | 否 | **可隐藏路径** → 使"目录清单里没有"这一推断更弱（与 `07` §9 的限制叠加） | **[B]**+**[E2]** |
| **NoMount metamodule**（可选） | overlay 挂载 | 否 | 若安装，`/vendor` 视图可能被覆盖 → 影响 A 类归属（U4-27） | **[B]**+**[U]** |
| 网络 / BPF / TMPFS / DroidSpaces / BBG | 与图形无关 | 否 | 无 | **[B]** |

> `MomenToMoiX` 这一名称在公开清单中没有稳定对应（工作流里出现的是 `use_momentx` 开关）。本文件**不替它编造语义**，只按"QoS 类"给方向性判断，并标 [U]。

### 4.3 对 Stage 4 结论的污染面

| Stage 4 结论类型 | 是否被污染 | 理由 |
| --- | :---: | --- |
| UAPI 契约（ioctl / 结构体 / 标志 / 属性 ID） | **否** | 纯源码比对，与运行内核无关 |
| 固件加载逻辑与版本校验 | **否** | 纯源码 |
| 设备文件存在性 / 大小 / 哈希（A 类） | **基本否** | `vendor` 未被本次安装改动；但 overlay 可见性未排除（U4-27） |
| 运行内核版本与模块装载（B/C 类） | **是** | 观测对象是第三方内核；结论须限定"在第三方内核上" |
| 性能 / 功耗 / 温控观测 | **是（且不可用）** | 调度与调频补丁直接改变这些量，不能代表原厂表现 |
| bootloop 判定（U4-10） | **否** | 本来就没有故障证据，仍为 UNKNOWN |

### 4.4 三条禁止推断

1. **不得**由"第三方内核能装载原厂 `.ko`"推出"r56p0 kbase 也能装载"——前者只证明 GKI KMI 未变，后者取决于 MTK 模块导出符号的 CRC。
2. **不得**由"换了内核 GPU 仍正常"推出"换 kbase 也安全"——kbase 是 GPU 栈的**根**，不是叶子。
3. **不得**把第三方补丁造成的帧率/功耗变化，记入"GPU 驱动性能"评价。

## 9. 本章净结论

1. **证据归属已澄清**：A 类（厂商文件）/ B 类（第三方内核运行时）/ C 类（厂商模块）三者的来源不同，此前一律记作"真机实测"是口径错误。
2. **安装范围已核验**：仅 `boot`；不碰 `vendor` / `vendor_dlkm`；不含 `.ko` / 固件 / `.so`。
3. **模块来源已分层**：设备 `.ko` 与仓库 `.ko` **不是同一构建**（vermagic 118 vs 143，决定性），只共享源码标签 `r49p1-03bet0`。**模块集合也不对称**：设备 13 个 GPU 链路模块中包含 `mtk_ghpm`，仓库 15 个文件里没有它；仓库的 3 个 `met_*` 在设备上未装载（§2.4、§3.6.3）。
4. **补丁影响已定性**：只能间接（调度/频率/温控/可见性），**不可能**改 GPU 驱动源码；性能类观测不可用于对比原厂。
5. **两项 P0 + 一项 P1 仍未闭合**：U4-04（行为面）、U4-12（固件实体）、U4-24（子项 a 待执行 / 子项 b 未开始）；Stage 5 可设计、不可定论、不可实施。
6. **口径更正一处**：`lsmod` 的 size 是内存尺寸而非文件大小，历史表述"`ged` 差 409 KB"已改为"方向参考"；D-007 主判据（vermagic）不受影响（§3.6.2）。
